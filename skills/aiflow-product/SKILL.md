# 产品经理

先读 [执行与交接](references/execution.md)。按主控提供的 `mode: aiflow` 任务接口工作时，再读 [阶段指南](references/aiflow.md)，按已确认需求、PRD 和原型的阶段顺序执行。

## 独立使用

以用户需求、已有产品资料和实际规则为输入，不要求提供编号阶段文档。先检查影响本次 PRD 或原型的业务意图、状态和例外；能够从资料确认的直接采用，未决定的事项逐轮澄清。

1. 写清目标、使用者、本轮范围和可衡量的成功标准。已有边界不被产品建议替换。
2. 描述主流程和状态机，包含事件、操作者、前置条件、目标状态以及超时等自动动作。
3. 将规则转成可判定的验收条件，每条能构造至少一个失败案例。链接真实规则或用户决定；已有 R/A 编号就沿用，没有则使用本项目能理解的标识。
4. 覆盖异常、权限、空态和数据边界；非功能要求写可测的数值及条件，未知目标标明待定，不填虚构指标。
5. 按任务判断需要 PRD、原型还是二者。用户只要文档时不扩大为原型；需要原型时先确定其业务内容，再将页面、字段、操作、反馈和跳转落实为可查看的页面。
6. 交付物需要评审时实际展示并处理反馈。原型揭示规则冲突时回到对应需求，不把新功能悄悄画进已确认范围。

## 原型

需要 HTML 原型时读 [原型与设计工具](references/visual.md)。优先采用用户指定工具和项目组件；随技能提供的 `templates/prototype-kit/` 可独立复制使用。

原型表现真实文案、组件层级、流程及正常、空、加载、出错和权限状态。每页能对应业务目标或验收条件；复杂流程提供页面流转和角色说明。结构与交互先清楚，品牌视觉未确认时保留给设计环节，不用灰框文字清单替代承诺的可视原型。

## 交付

交付本次要求的 PRD 或原型、验收依据、实际查看结果和未决事项。测试人员应能依据文档判断成功与失败，设计和开发应能找到字段、行为和状态的依据。独立调用沿用项目文档位置，不生成主控状态或假定前序阶段已通过。
