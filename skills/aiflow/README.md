# aiflow · 上手

一套把需求推到上线的流程。主智能体负责沟通与调度，八个专业角色默认由独立子智能体按十二阶段执行，配合用户确认、选型锁定、设计还原度、bug 清零和回归等门禁。

配套阅读：`SKILL.md`（规范）、`references/`（规则）、`experts/`（角色）、`templates/`（记录格式）。

## 五分钟上手

```
/aiflow 做一个设备巡检工单，班组长派单、执行人提交、班组长验收，超时自动升级
```

Codex 使用 `$aiflow`，例如 `$aiflow 继续`；下文的 `/aiflow` 示例替换入口即可。

然后：

1. 首次激活派需求分析师查证并展开问题，由主智能体和你对话澄清，不创建 `.aiflow/` 或问题文件。已有项目先读取现状，保留原有产物与执行模式。
2. **先问清，再统一写文件**：沿决策树问完当前能问的问题，给推荐与取舍，等你回答后展开下一层。问题全部解决、共识获确认后，才整理问题台账、状态和本阶段文档，再做产物评审；你明确要求中途保存时可以保存未完成的真实进度。
3. `/aiflow 继续` 逐阶段推进。**一次只推一格**。PRD、原型、设计和技术栈按确认点推进；设计阶段先让你看生图图片，有修改就改图，图片确认后才制作 HTML。
4. 每个阶段收尾，跑一次漂移检查：

```
python "<本 skill 目录>/scripts/check.py" "<项目目录>"
```

5. `/aiflow 状态` 随时看进度、待确认、未解决问题、未关闭缺陷。

## 第一次跑，你会看到什么

阶段 0 先问清产品目标、形态和期望能力，再协商本轮交付范围，不直接拍板技术方案。你会看到：

- 一个明确的边界：`本轮做：X ｜ 本轮不做：Y、Z、W`
- 一份风险线索（并发写入 / 数值精度 / 批处理），**不下技术结论**
- 一轮又一轮的问题，每轮只问当前能问的，直到没有遗留问题；没有问题就明确写「无」

默认优先使用当前工具支持的弹层或选项卡，直接选择并补充答案；不支持时退回编号文字。能力题可以多选，例如「Q4 A+C+D」，也可以明确回答都不需要；工具无法多选时，仅这类题改用文字，不改变题型。问题超过工具容量会分批展示，推荐组合只在你接受后生效。

范围足够小就不硬拆；需要拆分时保留完整产品目标，暂缓项不等于你不需要。

访谈从目的和场景展开，结合对象、用户路径、渠道、规模和实际约束继续深入，问题随回答变化。已明确的不再问，依赖未答前提的才延后。

问完一批还会检查答案带来的新分支，以及完整用户路径里的遗漏；确认共识后才收口。技术与部署约束在阶段 0 收集，具体选型在阶段 4 锁定。

## 提问时会提供哪些参考

每个阶段提问前先检查已有资料；公开案例、成熟方案或实现资料能帮助当前选择时，会主动联网查证，带着「别人怎么做、为什么适合或不适合这里、推荐什么」和来源链接来问你。已有有效证据可复用；没有相关分叉时不重复做完整调研。

需求调研阶段重点比较竞品、替代产品和开源实现：既看核心流程与异常处理，也看公开实现中的数据模型、关键代码和复用条件；不只列名称、功能或仓库链接。依据先留在对话中，澄清收口后再统一整理问题台账与调研报告。其他阶段按当前任务补查交互、技术、测试或部署做法。

不能联网、找不到合适案例或资料不足时会说明限制；用户要求不联网时遵守。案例用来帮助你作决定，不会自动变成需求或授权引入依赖。详细规则见 `references/research.md`。

## 它给你什么，不给你什么

**给**：需要时的产品原型和设计稿、可运行的骨架、数据模型、接口实现、单测、设计走查记录、端到端用例、发布与回滚方案，以及可追溯的留档。

**不给**：生产级权限体系、高并发调优、安全审计、第三方系统对接、业务决策。

最后一条最关键：**它不替你做业务判断**。所有"该用哪种口径""该不该允许"的问题，它都会停下来问你。让 AI 替你定业务规则，等于把一个错误埋进数据模型，后面每个阶段都会忠实地实现它。

## 常见问题

**一句话能直接出代码吗？**
不能。一句话只能进阶段 0，产出的是边界和问题清单。要代码，得走完前六个阶段。

**要我确认几次？**
常规确认覆盖范围、需求、PRD、产品原型、设计图片、最终 HTML 设计稿和技术栈。不需要原型或设计稿时减少对应评审。需要澄清时先问清再落档；同一完整结论不机械重复确认，也不把图片认可当作对未展示的 HTML 细节的认可。每个点可多轮，回归有条件放行另需确认条件；用户未回复不算确认。

**什么时候会出原型和设计稿？**
产品经理在 PRD 里判断并写理由，你确认 PRD 时一起确认。纯接口、批处理、只改字段文案的需求通常都不需要，阶段 3 和阶段 7 会跳过。原型图做到中保真：用组件库的真实组件和真实文案，品牌视觉留给设计稿。

设计阶段顺序为：**澄清视觉要求 → 生图 → 展示与修改图片 → 用户确认 → 按图制作 HTML → 浏览器截图核对与修正 → 最终交付**。确认原图留在 `.aiflow/design-images/`，版本和反馈记在 `design-images.md`；HTML 及其浏览器截图留在 `.aiflow/design/`。生图不可用时如实说明，不把 HTML 截图冒充先行设计图，也不提前制作整套 HTML。

**公司或甲方已有设计规范，怎么让它用上？**
每个项目的规范记在 `.aiflow/design-system.md`，团队默认规范放在 `~/.aiflow/design-system.md`，格式见 `templates/design-system.md`。阶段 2 会先读项目代码和你给的规范文件，都没有才问你。原型构建时自动套用里面的设计令牌（主色、圆角、字体等）。详见 `references/design-system.md`。

**能添加自己的前端、后端开发规范吗？**
可以，直接提供已有 Markdown，前后端可分别配置。项目默认放 `.aiflow/frontend-standards.md`、`.aiflow/backend-standards.md`；团队默认放 `~/.aiflow/` 下同名文件。文件在其他位置时，把路径告诉 AI，它会登记到 `state.yaml.development_standards`；相对路径以项目根目录为准，原文无需改格式。

优先级是显式指定、项目规范、团队默认；都没有时沿用项目现状。架构师先读规范再定方案，前后端开发及修复都遵循，JOB 也遵循后端规范；开发日志留实际自检记录。示例模板为 `templates/frontend-standards.md`、`templates/backend-standards.md`，完整规则见 `references/development-standards.md`。

**能指定技术栈或框架吗？没指定会推荐吗？**
可以。直接说明语言、框架、数据库或版本要求，以及哪些必须遵守、哪些只是偏好；也可写进开发规范。阶段 4 先查证事实，对影响方案的未知决策逐轮追问，未指定部分带推荐和取舍，已有项目优先建议沿用。共识收口后才将具体组合、版本范围、理由与备选写入 `.aiflow/tech-stack.md`，经你评审确认后锁定，不会先写一套文件再用一句“是否确认”代替访谈。

开发、测试和发布都以已锁定组合为准；更换技术或超出版本范围要重新确认，不能因开发遇到困难擅自换框架。门禁检查确认、方案指纹和逐项开发核对记录；版本范围与兼容性还需用实际项目和对应生态工具验证，不靠记录自证。详见 `references/tech-stack.md`。

**还原度 90% 怎么算？**
体验设计师在设计稿确认时就定好走查点清单。走查时逐点判定，还原度 = 通过的点 ÷ 全部的点。90% 以上、并且关键项（页面存在、交互实现、空 / 加载 / 出错状态）全部通过才算通过。

**必须十二个阶段都跑吗？**
不必。小改动可以 `/aiflow 跳到 4`，但会先检查前一阶段的留档物在不在。跳阶段不等于跳留档。

**一个人用行吗？**
行。新项目默认主智能体和你沟通，需求、产品、设计、架构、前端、后端、测试与运维分别派独立子智能体。按阶段启动，前后端任务互不冲突时可并行；修复优先交回原角色，测试和走查独立验收。不是每次同时开八个会话。

环境不支持子智能体或你选择单会话时，会说明并记录为模式 1 角色切换；需要独立验证的部分仍须实际完成。已有项目通常保留原模式，升级或降级都从当前交接记录，旧记录保留。具体交接见 `references/orchestration.md`。

**子智能体做完就关闭吗？角色共用吗？**
一个角色使用自己的上下文，同角色跨阶段可复用，但每阶段都要重新派任务并等结果。例如 0→1 可续派同一分析师，2 则创建产品经理。任务完成后可空闲保留；需要释放名额时保存结果再关闭，后续恢复或新建同角色。不同角色不共用一个子智能体。

`agent_sessions` 仅记录身份，`stage_dispatch` 记录当前阶段的实际执行。进入新阶段前先更新阶段并派工，不能沿用旧 ID 就由主会话直接写下一阶段文档；旧项目续跑从本次任务补真实记录，不补造过去的派工。

**需求变了怎么办？**
业务变更从事实源改，不在下游产物里单改。先留 history 快照，把待复核产物登记到 `state.invalidated_artifacts`，回到最早受影响阶段并重置相关旧结果，再逐阶段重做与确认。失效文件可留作追溯，但不能作为当前输入；未关闭问题要迁移或明确处置，不会因回退直接消失。规则见 `references/change.md`。

**跑完之后呢？**
归档 `.aiflow/` 整个目录。下次同类项目，把 `facts.md` 当起点改，比从零开始省一半时间。

## 从旧版迁移（十阶段 → 十二阶段）

`state.yaml` 没有 `flow_version: 2` 的项目，`check.py` 会直接阻塞。迁移步骤：

1. `state.yaml` 补字段：`flow_version: 2`、`open_ux_issues: []`、`signoffs`（五项先填 `pending`）、`prototype_required`、`design_required`、`walkthrough_result`。参照 `templates/state.yaml`。
2. 产物改名：`03-arch → 04-arch`、`03-mapping → 04-mapping`、`04-tasks → 05-tasks`、`05-dev-log → 06-dev-log`、`06-test-report → 08-test-report`、`07-bugs → 09-bugs`、`08-regression → 10-regression`、`09-release → 11-release`；同步 `artifacts` 列表，`stage` 按新编号换算。
3. 新建 `questions.md`，把旧的 `pending_decisions` 和阶段 0 的待确认问题搬进台账，`pending_decisions` 改成只写问题编号。
4. 已经过了的确认点，**请用户重新确认**，在各产物的「用户确认」小节记下用户原话。AI 不得替用户补填。
5. 跑 `check.py`，按阻塞项逐条补齐。

已有十二阶段项目更新本 skill 后，也要重跑 `check.py`：设计稿每页补齐维度为「版式」的关键走查点，交互走查点核对页面归属并标为关键项。已确认的走查点需要调整时，按 `references/change.md` 重新评审，不得直接修改冻结清单。

先图片后 HTML：新模板包含 `design_image_status` 与 `design_image_fingerprint`，阶段 3 用 `templates/design-images.md` 记录实际生图和确认。图片确认后运行 `check.py <项目目录> --design-image-fingerprint` 保存当前基准指纹，再制作 HTML；图片待评审时门禁阻止提前推进，但不催交 HTML。已过阶段 3 且没有这两个字段的旧项目可保留已完成 HTML 历史，不补造生图记录；重新进入阶段 3 做新设计时采用新流程。

澄清门禁：阶段 0–4 需要 `clarification` 对应当前阶段，按 `references/clarification.md` 补真实共识记录；已有输入完整明确时可写 `not_needed` 并说明依据。本阶段有非作废问题须记录共识确认；未收口就保持 `pending`，此时检查器不会要求先补正式文件。阶段 5–11 无新分叉时兼容旧记录，发现新决策则重新开启澄清。已有真实确认保留，不补造历史访谈或用户原话。

阶段 8 及以后的项目，还需按 `templates/bugs.md` 给已关闭缺陷补齐真实复测记录，不能从一句「通过」反推或编造执行证据；没有证据就重新复测。初测失败报告不回写，回归重跑所有当前有效 A 对应的初测 E。有条件放行按 `templates/regression.md` 核对条件并补用户确认记录，AI 不得代填。

开发规范是可选功能：旧项目没有 `development_standards` 字段仍可续跑；若发现或已指定规范，需完整读取并在开发日志补实际检查证据，不能只补一行「通过」。

技术栈锁定从阶段 4 起必需：已有项目按 `templates/tech-stack.md` 补录实际选型、版本与约束，请用户确认具体组合后，用 `check.py <项目目录> --tech-stack-fingerprint` 生成指纹，再填写 `tech_stack_status: locked` 与 `tech_stack_fingerprint`。阶段 6 起还需在开发日志补真实逐项核对记录；不得编造历史确认或用预期版本冒充实际版本。阶段 0–3 不受此新增门禁影响。

没有 `invalidated_artifacts` 的旧项目仍可续跑；发生回退或变更时，按变更协议补清单与状态重置。当前实现/验收表中的作废 A 需要移除或改为有效编号，旧记录归档保留，不得为了放行删除历史。

## 后续验证

当前自动化测试覆盖门禁放行、阻塞及阶段 8–11 的状态流转，也覆盖验收语义升版后保留快照、回退 PRD、重新确认并逐阶段重跑到发布，以及不升 facts 版本的设计重审、旧结果拦截和未关闭问题迁移。它们用临时夹具模拟角色动作，不代表真实开发或发布。

改动澄清策略时，另用隔离目录和独立上下文试跑一句话请求及后续答复，检查实际覆盖、依赖、推荐和停止行为；保存过程记录，不能用固定文案匹配或门禁用例数量证明回复质量。

另有真实 Chromium 的桌面、手机视口回归，覆盖版式偏移、换行溢出、规范取值、隐藏与标注层、根节点检查，以及固定版本的 70 项组件对照、故意改尺寸和缺失组件反例。后续重点：

- 用一个真实纵切试跑阶段 4–11，保留代码执行、缺陷修复、发布与回滚演练的实际证据。

维护本 skill 后运行：

```
python "<本 skill 目录>/tests/test_check.py"
```

改动浏览器检查脚本、样式包或组件对照页面时，还要运行浏览器维护测试。需要 Node.js、npm 和 Chromium；依赖只装在测试目录，不是使用本 skill 或运行 Python 门禁的前置条件：

```bash
cd "<本 skill 目录>/tests/browser"
npm ci --ignore-scripts
npx playwright install chromium
npm test
```

依赖和浏览器首次安装需要网络；测试本身用真实页面及锁定的本地组件库资源拦截所有请求，不连接 CDN，也不需要启动服务。失败时在 `test-results/` 留截图、错误上下文和 trace；本地依赖与输出不进仓库。组件对照页面的固定版本和测试依赖一起升级，不能用浮动版本替换已验证基线。
