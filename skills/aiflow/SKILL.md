# aiflow — AI 全流程交付工作流

## 一、激活与调用

本文以 `/aiflow` 写命令示例；Codex 使用 `$aiflow`，后面的参数相同，例如 `$aiflow 继续`。入口后的具体需求决定流程范围，不能把对 skill 本身的维护请求当成新项目启动。

| 指令 | 行为 |
|---|---|
| `/aiflow <一句话需求>` | 从阶段 0 的对话澄清开始，问清后再建文件 |
| `/aiflow 继续` | 先核对并派工当前未完成阶段；当前阶段通过门禁后才进入下一阶段。需要执行的每个阶段都走下方「每阶段进场」 |
| `/aiflow 状态` | 打印当前阶段、留档物、失效待复核产物、待确认、未解决问题、未关闭缺陷与走查问题单 |
| `/aiflow 跳到 <阶段号>` | 允许跳，但先补前一阶段的留档物检查，缺失就拒绝 |
| `/aiflow 回退 <阶段号>` | 按 `references/change.md` 保留快照、登记本阶段待重做及下游待复核产物、重置相关结果；不能只改阶段号 |
| `/aiflow 改 <变更描述>` | 先澄清变更，再按 `references/change.md` 分类处理事实源、开发规范与技术栈；复核影响，已确认的变更重新确认 |

> 主智能体统一对接用户；八个角色是内部专业分工，默认按 `references/orchestration.md` 由阶段执行协调器派独立子智能体执行。

### 首次激活先访谈

1. 以用户当前项目为根目录；若 `.aiflow/` 已存在，读取状态并续跑，**不得覆盖**。`state.yaml` 没有 `flow_version: 2` 的旧项目，按 `README.md`「从旧版迁移」处理。
2. 新项目先读 `references/orchestration.md` 和追问协议，新建阶段 0 执行协调器，由它派需求分析师做查证与问题分析；主会话组织提问、等待答复并继续展开。此时不创建 `.aiflow/`、问题文件或占位产物；没有状态文件时，`继续` 和 `状态` 依据当前对话处理。
3. 当前阶段的问题全部解决、共识获确认后，按 `references/clarification-records.md` 统一整理台账、状态和阶段产物。已有项目的新一轮澄清按追问协议标记 `pending`，保留原产物，问清后再更新。
4. 阶段 0 使用 facts v0；阶段 1 需求收口后才创建 `.aiflow/facts.md` v1。模板和门禁在落档时读取，不作为访谈前的填表任务。
5. 每阶段收尾运行 `python "<本 skill 目录>/scripts/check.py" "<项目目录>"`。退出码必须为 0 才能推进；1 是阻塞，2 是仍有警告。

### 每阶段进场，包括继续、回退和重做

每进入一个需要执行的阶段，先按 `references/orchestration.md` 确定对应角色。模式 2/3 由主会话新建本阶段执行协调器，协调器为该角色新建子智能体并发送本阶段任务，同阶段续做时才恢复本阶段的原会话；原生嵌套确实不可用时才由主会话直接派角色，记为 `strategy: direct`。**读取专家文件或发现旧会话 ID，都不算派工。** 同角色换阶段也要新建子智能体、重新派任务并等待返回，主会话和协调器都不代写专业产物。模式 1 按已说明的角色切换方式执行，不伪造工具派工记录。

已有状态文件时，先把 `stage` / `expert` 设为正在执行的阶段与角色，模式 2/3 重置 `stage_dispatch` 与 `stage_execution`，取新的执行序号，把本阶段派出的会话逐条追加到 `session_log`；不是写完下一阶段产物才补阶段号。阶段 0–4 重置本阶段澄清状态，阶段 5–11 仅遇到新决策时重开澄清。首次阶段 0 仍先在对话中派工与澄清，收口后才建文件。

模式 2/3 收到本阶段实际结果后，主会话在 `stage_dispatch` 记录对应角色的本次派工与完成返回依据，在 `stage_execution` 记录执行方式与协调器交接依据，再按 `references/gates.md` 收尾。阶段 2 的 PRD → 原型、阶段 3 的图片 → HTML、修复 → 复测等同阶段后续工作，也要实际向相应角色派新任务，不能凭之前的一次完成直接接手。

**回退与变更**：按 `references/change.md` 维护 `state.invalidated_artifacts`。角色交接只传当前有效产物，history 和失效文件仅用于追溯；当前阶段必需的失效项在重做、复核及必要确认前不能使用，旧任务和验收结果也不能随之复用。

**用户开发规范**：阶段 4 前按 `references/development-standards.md` 读取可选前后端 Markdown 规范，项目默认位置分别为 `.aiflow/frontend-standards.md`、`.aiflow/backend-standards.md`，也支持显式路径与团队默认。已配置就遵循，开发、走查修复、缺陷修复均适用；没有配置时沿用项目现状，不要求补文件。

**技术栈选型**：先按追问协议澄清用户指定、偏好及实质取舍，未指定部分在问题中主动推荐，已有项目优先建议沿用。澄清收口后按 `references/tech-stack.md` 将具体组合、版本范围、理由与取舍记入 `.aiflow/tech-stack.md`，评审确认后锁定；开发和修复不得擅自换栈或超出锁定范围。

## 二、五条铁律

1. **一次只推进一个阶段。** 跳过的确认会在验收时连本带利还回来。
2. **先在对话中问清，再统一写文件。** 问题台账同样在收口后整理；留档完成后才能推进阶段。
3. **判断不了必须问，不要替用户编。**
4. **必查项不等于必填项。** 每一节要求你做的是一次**判断**，不是填满表格。结论可以是「不适用」，但必须写明理由；**不允许空白跳过，也不允许为了填满而硬写**。
5. **要用户确认的节点，只认用户本人的明确确认。** 用户没回、回答含糊、AI 觉得"应该没问题"，都不算确认。

## 四、追问与确认

**全部角色需要澄清时都读 `references/clarification.md`**，按决策树持续访谈，优先调用可用的交互式提问工具，受限时再用文字。它是提问、推荐、等待答复与收口的统一入口。

**提问前先准备证据**：每阶段检查已有资料；外部案例或成熟方案有助于当前选择时，按 `references/research.md` 主动联网查证，把实际做法、来源、适用条件和取舍带给用户。阶段 1 默认调研竞品、替代产品与开源实现；其他阶段按需补查。外部案例不能代替用户决定，也不能绕过已有范围、事实源和技术栈确认。

访谈收口后才按归档协议整理 `questions.md` 和 `state.clarification`。要用户评审留档物的节点随后按 `references/review.md` 走：交付 → 评审 → 修改 → 再交付，直到明确确认。评审引出新的不确定性，先回澄清，不能边猜边改。

| 确认点 | 阶段 | state 字段 | 确认什么 |
|---|---|---|---|
| 范围 | 0 | `signoffs.scope` | 本轮做什么、不做什么 |
| 需求 | 1 | `signoffs.requirement` | 规则都问清了，没有遗留问题 |
| PRD | 2 | `signoffs.prd` | PRD 没问题，含要不要原型、要不要设计稿 |
| 产品原型 | 2 | `signoffs.prototype` | 原型没问题；不需要时 `skipped` |
| 设计图片 | 3，制作 HTML 前 | `design_image_status` + `design_image_fingerprint` | 当前生图版本的视觉方案已认可，允许据此制作 HTML |
| HTML 设计稿 | 3 | `signoffs.design` | 最终设计稿没问题；不需要时 `skipped` |
| 技术栈 | 4 | `tech_stack_status` + `tech_stack_fingerprint` | 展示过的具体选型、版本范围、理由与取舍，确认后 `locked` |

确认记在产物的「用户确认」小节：确认结论、用户原话、确认时间。**用户原话只能来自用户本人的消息**；子代理接触不到用户，追问和确认只在主会话做。

## 五、阶段 0 是关口

用户说的大多是大词：「做一个企业智能客服」「做个数字化平台」。

阶段 0 先读 `references/discovery.md`，展开产品决策树，再做以下判断：

1. **判断目标与范围**：按产品发现协议覆盖用途与成功标准、用户与业务模式、核心对象、渠道、完整任务、真实运行、规模、既有约束及外部依赖。已有明确输入不重复问；这些根前提足够明确后，才判断当前纵切是否适合本流程。
2. **判断形态**（这一条决定后面的阶段长什么样）：

   | 形态 | 特征 | 本流程适配度 |
   |---|---|---|
   | **流程型** | 有状态流转、多角色、有先后 | 高，默认形态 |
   | **计算型** | 核心是算得对（金额、折扣、分账） | 中，要额外强调"边界值与精度"用例 |
   | **批处理型** | 定时跑、导入、对账、可重跑 | 中，任务要标 `JOB`，测试要测断点续跑 |
   | **并发型** | 存在同时写入的可能（抢库存、抢号、抢状态） | **阶段 0 只标线索，不下结论**，怎么处理交给架构师判断 |
   | **效果型** | 核心是产出质量（摘要好不好、推荐准不准、识别对不对） | **低，必须先降维**："好不好"不可判定，得换成"符合某条可判定的规则"才能开工 |

3. **标出风险线索，不下技术结论**：有同时写入的可能标「存在并发写入」，涉及金额、费率标「涉及数值精度」，定时、导入、对账标「批处理」。架构师看到线索后可以判断"本项目不涉及"，但必须写下理由。**"不会"是允许的答案，"没判断"不允许。**
4. **切纵切**：范围过大时提出可独立验收的候选纵切，解释它们保留的价值和暂缓项，由用户确认本轮选择；范围已足够小则不硬拆。单个纵切可以包含用户选定的多项配套能力。
5. **确认范围**：按追问协议探索各条分支，反查完整用户路径的遗漏；问清后在对话中展示「本轮做 / 本轮不做」和默认项，确认共识，再统一落档。

产物 `00-intake.md` 里必须有两句：

> 本轮做：<纵切名>　｜　本轮不做：<其余纵切列表>
> 形态：<流程型 / 计算型 / 批处理型 / 并发型 / 效果型>　｜　风险线索：<并发写入 / 数值精度 / 批处理 / 无>

缺任一句，或者用户没有确认范围，不许进阶段 1。

## 六、产品原型、设计稿与设计走查

**要不要**：产品经理在 PRD 的「交付形态判断」里写明要不要原型、要不要设计稿及理由，用户确认 PRD 时一起确认，同步到 `state.yaml` 的 `prototype_required`、`design_required`。两者互相独立，判断依据见 `experts/pm.md` 与 `experts/ux.md`。需要其中任何一个时，再按 `references/design-system.md` 确定设计规范，记进 `.aiflow/design-system.md`，原型、设计稿、前端开发都用它。

**产品原型**（阶段 2，PRD 确认之后）：页面编号 `P1..Pn`，每页写清服务哪几条 A、字段、操作、状态、跳转。做到中保真（规范见 `references/prototype.md`）：用组件库的真实组件、真实文案和功能色，有全局说明、页面流程图、角色 × 状态矩阵，每页带编号标注；有设计规范时用规范的令牌，没有时品牌视觉留给设计稿。默认用 `templates/prototype-kit/` 出 HTML，放在 `.aiflow/prototype/`，样式内联，另导出 PNG。

**设计稿**（阶段 3）：按 `experts/ux.md` 先调用生图能力制作设计图片，主会话展示、收集反馈，设计师修改图片，循环到用户明确确认。图片与反馈保存在 `.aiflow/design-images/` 和 `design-images.md`。图片确认前不编写设计 HTML；确认后以原图为视觉基准制作 `.aiflow/design/` 下的 HTML，补齐真实文字、组件、交互状态与响应式，实际打开浏览器截图并修正还原偏差。

最终 `03-design.md` 记录图片还原核对、交互标注 `I1..In`、走查点 `W1..Wn` 与设计稿自检。W 引用同页真实 I，每页有关键版式点；完成规范、版式和组件核对后，由 `design_reviewer` 对照确认图片与 HTML 独立评审，再交用户确认最终设计稿。走查点随最终设计稿冻结，开发前公开。图片评审期间门禁等待图片确认，不要求先交 HTML 或最终自检。

**设计走查**（阶段 7，前端开发完之后）：体验设计师在浏览器里打开页面，逐个走查点判定。

- 还原度 = 通过的走查点 ÷ 全部走查点，每个走查点取最近一轮的结果
- **≥ 90% 且关键项全部通过才算通过**。关键项：页面存在且可达、交互标注逐条实现、空 / 加载 / 出错状态存在、每页的通用版式点
- 不达标的点逐条开成走查问题单 `UX-n` 派给前端；前端改完改成「待复查」并通知体验设计师；体验设计师复查后重算还原度，循环到通过为止
- 通过时仍未达标的非关键点记为「遗留」，写进走查结论

阶段 9 前端修缺陷改到已走查的页面时，体验设计师复查受影响的走查点，回归报告写「设计还原复核」。

## 七、任务编号是主键

阶段 5 拆出的每个任务都有编号 `T1..Tn`，并带类型：`FE`、`BE` 或 `JOB`；JOB 由后端开发负责。有原型或设计稿时，每个页面 `P` 至少落到一个 FE 任务。

粒度标准：**一个人能独立开发完、另一个人能独立验收的单元。** 通常对应一个接口或一个页面。

任务编号贯穿全流程：

- 开发日志按任务记：`T3(BE) 完成`
- 测试报告按任务测：`T3 通过 / T5 失败`
- 缺陷挂任务，**并按任务类型自动派给对应开发**：`BUG-2 · 关联 T5(FE) · 派给前端`
- 回归按任务推范围：`受影响任务：T5、T7`

## 八、缺陷往返协议（阶段 9）

```
测试开单（挂任务 + 派单） → 状态「待修复」
    ↓
对应开发修复 → 填「修复说明 + 待验点」 → 状态「待复测」
    ↓
测试复测 → 通过「已关闭」 ／ 不通过「打回」并写清原因
    ↓
打回 → 回到原开发，重新进入循环
```

五条硬规矩：

1. **不许口头传。** 修了什么、让验什么，必须写在单子上。
2. **一次只改一个缺陷。** 夹带两个修复，出问题无法定位，也没法做单点复测。
3. **复测只验这一个**，不顺带测别的。
4. **打回必须写原因**：现象、环境、复现步骤。不许只写"还是不行"。
5. **不许跳过复测进回归。** 单个 bug 没验过，回归结果不可信。

阶段 7 的走查问题单走同一个循环，复查人是体验设计师。

阶段 9 的复测按 `templates/bugs.md` 逐轮追加 E/A、结果和证据，每个用例以最大轮次为准；初测失败报告保持不变，当前验收状态按 `experts/tester.md` 的规则从复测和回归结果更新，不能改写历史来消除冲突。

## 九、清零门禁（阶段 9 → 10）

**必须满足全部三条，才允许进入全量回归：**

- [ ] `state.yaml` 的 `open_bugs` 为空
- [ ] `09-bugs.md` 里没有「待修复」「待复测」「打回」状态的单子
- [ ] 每条已关闭缺陷都有测试填写的有效复测记录和当前通过结论，最新一轮没有失败

任何一条不满足 → 停在阶段 9，不许往下走。

**回归门禁只有一个判定**：结论为「通过」且无遗留条件，或结论为「有条件通过」且文档与 state 的条件逐项一致、用户原话和确认时间已记录，才允许上线；「不通过」、结论缺失或无法解析都直接退回。进入回归前 `pending_decisions` 必须为空；所有当前有效 A 及初测中关联它们的全部 E 必须重跑并通过，回归收尾时 `acceptance_results` 全部 `pass`。

## 十、主智能体调度，专业角色独立执行

**新项目默认模式 2。** 主智能体主持澄清与确认、维护状态并验收结果；每个需要执行的阶段新建执行协调器，由它派工、安排重试与独立评审，向主会话回传精简结果；八个专业角色按阶段由独立子智能体执行。每次启动协调器或角色前读取 `references/orchestration.md`，按其中的交接表与写入边界实际调用子智能体工具。

| 模式 | 使用方式 |
|---|---|
| **2 子智能体隔离（默认）** | 主智能体 → 阶段执行协调器 → 专业角色，各用独立上下文；原生嵌套不可用时主智能体直接派角色；按需启动，前后端工作独立时可并行 |
| **1 角色切换（兼容）** | 用户选择或环境无法使用子智能体时，由同一会话执行；说明原因，不声称上下文独立 |
| **3 换人 / 换模型** | 在角色调度基础上，由独立人员或不同模型完成高风险终验 |

已有项目通常沿用记录模式；升级或能力受限降级时，从当前交接记录实际模式并保留历史，不把角色切换记成子智能体执行。新项目访谈期间，会话 ID 先保留在对话中，共识收口后才写入 `agent_sessions`、`stage_execution` 与 `session_log`，不为调度提前建文件。

测试和设计走查不接收开发对话与实现理由；独立设计稿评审使用 `design_reviewer`，不能由出稿会话自评。会话隔离并不等于不同模型；模式 1 的待验点、按验收标准测试和断点记录也不能替代独立验收。

### 高风险终验

涉及金额、权限或状态机的关键改动，高风险模块上线前，或曾出过事故的模块，仍按模式 3 做独立终验。记录 `agent_sessions.final_reviewer`（`human:<姓名>` 或 `model:<名称>`）、`final_review_result` 和 `final_review_evidence`。独立终验未实际完成时，不能声称通过或上线；其他正式项目由模式 2 的独立测试上下文终验。

## 十一、执行中遇到新决策

产品、业务或技术取舍尚不明确时，回到 `references/clarification.md` 访谈，暂停依赖该答案的执行。能查证的事实自行查证；命名、目录等实现惯例遵循已有规范。不可逆操作或影响范围无法判断时，先解决授权与影响问题。

## 十三、漂移控制

模型执行这套流程时，漂移是必然的：爱写的多写，不爱写的略过；这次三节，下次八节；同一概念换个说法。光靠"写的时候注意"没用，漂移发生时毫无察觉。

| 形态 | 表现 | 办法 | 能否自动 |
|---|---|---|---|
| **漏** | 14 条标准只落了 11 条 | 编号台账，分母是全集，差集就是漏 | ✅ 脚本 |
| **编** | 引用了不存在的编号 | 编号必须能在 facts 和产物里找到定义 | ✅ 脚本 |
| **滑坡** | 产物结构忽大忽小 | 最小可检索单元（只规定必须能被找到，不规定骨架） | ⚠️ 半自动 |
| **失真** | 下游读出来跟你写的不是一回事 | 让下游**复述**，不是"读一遍说 ok" | ❌ 人工 |

### 每阶段收尾跑一次

```
python "<本 skill 目录>/scripts/check.py" "<项目目录>"
```

先检查澄清记录和问题台账；澄清未完成时阻塞，但不要求先造正式产物。阶段 3 在图片确认与指纹有效后才检查 HTML 产物，图片待评审时不催交 HTML。随后检查用户评审确认、设计与开发规范、技术栈锁定和实际核对、产物有效性、事实源与编号覆盖、设计自检与走查、任务、缺陷复测、回归和发布终态。

退出码：0 通过 / 1 有阻塞项 / 2 只有警告。**退出码不是 0 就不许进下一阶段。**

脚本能查确认字段、自检结论和编号对应，查不了用户原话是否真实、浏览器检查是否实际执行、评审人是否独立。这些仍须保留真实消息和检查证据，不能把脚本通过当成已经执行过检查。

### 复述校验（脚本做不到的那部分）

阶段 4 收尾，让测试角色做两件事：

1. 用自己的话复述"这条验收标准靠什么保证"
2. 与方案原文对照

复述不出来，或者复述得比原文宽松，就是失真。**"读一遍说没问题"不算，那是走过场。**

## 十四、通用性要求

- skill 文件里**不许出现具体项目名**，示例用中性词或多行业轮换。
- `state.yaml` 的 `project` 由用户输入决定。
- 行业特有规则（客服 SLA、巡检超时、制造公差）只出现在用户填的事实源里。
- 换项目时 skill 一个字不改，只改 `.aiflow/` 下的内容。

## 十五、适用边界

**能处理**：围绕一个核心业务对象的完整主流程，规则可判定，业务取舍有明确决策人。按实际复杂度协商交付范围，不用状态数或规则数限制澄清。

先明确完整产品目标，再协商本轮可交付边界，保留必要流程与真实业务要求。

**处理不了**：多系统集成（呼叫中心、支付、OCR）、规则还在探索期、要生产级（权限体系、高并发、安全审计）、已有系统小改。

遇到大词，**不拒绝也不硬吞**：在阶段 0 先问清产品目标，再切成纵切，按用户确认的起点交付；完整目标保留，不把暂缓项当成用户不需要。
