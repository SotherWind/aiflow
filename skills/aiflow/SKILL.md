# aiflow — AI 全流程交付工作流

## 一、激活与调用

| 指令 | 行为 |
|---|---|
| `/aiflow <一句话需求>` | 建流程，进阶段 0（澄清），**不直接进开发** |
| `/aiflow 继续` | 推进到下一阶段 |
| `/aiflow 状态` | 打印当前阶段、留档物、待决策、未关闭缺陷 |
| `/aiflow 跳到 <阶段号>` | 允许跳，但先补前一阶段的留档物检查，缺失就拒绝 |
| `/aiflow 回退 <阶段号>` | 回退，并把下游产物标记为失效 |
| `/aiflow 改 <变更描述>` | 走变更流程：先改事实源 → 算影响面 → 按编号重跑（见 `references/change.md`） |

> ⚠️ 七个角色是**内部角色**，不是斜杠命令，不对外暴露。唯一入口是 `/aiflow`。

### 首次激活先初始化

1. 以用户当前项目为根目录；若 `.aiflow/` 已存在，读取状态并续跑，**不得覆盖**。
2. 新建 `.aiflow/artifacts/`，复制 `templates/state.yaml` 为 `.aiflow/state.yaml`，复制 `templates/intake.md` 为 `artifacts/00-intake.md`，新建 `.aiflow/breakpoint-log.md`。
3. 填写 `project`，保持 `stage: 0`、`facts_version: 0`，并在 `artifacts` 登记 `00-intake.md`。阶段 0 使用 facts v0，**此时不要求 `facts.md` 存在**。
4. 进入阶段 1 时复制 `templates/facts.md` 为 `.aiflow/facts.md`，从 v1 开始填写；每进入一个阶段，复制对应模板并先更新 `state.yaml`。
5. 每阶段收尾运行 `python "<本 skill 目录>/scripts/check.py" "<项目目录>"`。退出码必须为 0 才能推进；1 是阻塞，2 是仍有警告。

## 二、四条铁律

1. **一次只推进一个阶段。** 跳过的确认会在验收时连本带利还回来。
2. **没有留档物，这一阶段就不算完成。** 口头结论不算。
3. **判断不了必须问，不要替用户编。**
4. **必查项不等于必填项。** 每一节要求你做的是一次**判断**，不是填满表格。结论可以是「不适用」，但必须写明理由；**不允许空白跳过，也不允许为了填满而硬写**。

## 四、阶段 0 是关口

用户说的大多是大词：「做一个企业智能客服」「做个数字化平台」。

阶段 0 做四件事：

1. **判断范围**：能用一个名词说清业务对象吗？规则能在 8 条以内吗？
2. **判断形态**（这一条决定后面九个阶段长什么样）：

   | 形态 | 特征 | 本流程适配度 |
   |---|---|---|
   | **流程型** | 有状态流转、多角色、有先后 | 高，默认形态 |
   | **计算型** | 核心是算得对（金额、折扣、分账） | 中，要额外强调"边界值与精度"用例 |
   | **批处理型** | 定时跑、导入、对账、可重跑 | 中，任务要标 `JOB`，测试要测断点续跑 |
   | **并发型** | 存在同时写入的可能（抢库存、抢号、抢状态） | **阶段 0 只标线索，不下结论**——"这里有并发写入"，怎么处理交给架构师判断 |
   | **效果型** | 核心是产出质量（摘要好不好、推荐准不准、识别对不对） | **低，必须先降维**——"好不好"不可判定，得换成"符合某条可判定的规则"才能开工 |

3. **标出风险线索，不下技术结论。** 阶段 0 的职责是提醒，不是拍板：

   | 线索 | 阶段 0 做什么 |
   |---|---|
   | 有同时写入的可能 | 标一句「存在并发写入」，交付架构师判断 |
   | 涉及金额、费率、分摊 | 标一句「涉及数值精度」，交付架构师判断 |
   | 定时、导入、对账 | 标一句「批处理」，任务标 `JOB` |

   > 阶段 0 只负责"让后面的人知道要看这里"，**不负责给出技术结论**。架构师看到线索后，可以判断"需要专门设计"，也可以判断"本项目不涉及"——但必须写下理由。
4. **切纵切 + 问开工阻塞问题**：拆成 4–8 个纵切，只选第一个开工；最多问 3 个（多角色或变长审批链可到 4 个），没有就写「无」；然后**停下等回答或范围确认**，不得硬凑问题。

> 并发线索交到阶段 3 之后，架构师要回答一句：这些写入会不会互相破坏？会 → 给策略；不会 → 说明理由（单用户、串行执行、只读）。
> **"不会"是允许的答案，"没判断"不允许。**

产物 `00-intake.md` 里必须有两句：

> 本轮做：<纵切名>　｜　本轮不做：<其余纵切列表>
> 形态：<流程型 / 计算型 / 批处理型 / 并发型 / 效果型>　｜　风险线索：<并发写入 / 数值精度 / 批处理 / 无>

缺任一句，不许进阶段 1。

## 五、任务编号是主键

阶段 4 拆出的每个任务都有编号 `T1..Tn`，并带类型：`FE`、`BE` 或 `JOB`；JOB 由后端开发负责。

粒度标准：**一个人能独立开发完、另一个人能独立验收的单元。** 通常对应一个接口或一个页面。

任务编号贯穿全流程：

- 开发日志按任务记：`T3(BE) 完成`
- 测试报告按任务测：`T3 通过 / T5 失败`
- 缺陷挂任务，**并按任务类型自动派给对应开发**：`BUG-2 · 关联 T5(FE) · 派给前端`
- 回归按任务推范围：`受影响任务：T5、T7`

## 六、缺陷往返协议（阶段 7）

```
测试开单（挂任务 + 派单） → 状态「待修复」
    ↓
对应开发修复 → 填「修复说明 + 待验点」 → 状态「待复测」
    ↓
测试复测 → 通过「已关闭」 ／ 不通过「打回」并写清原因
    ↓
打回 → 回到原开发，重新进入循环
```

五条硬规矩：

1. **不许口头传。** 修了什么、让验什么，必须写在单子上。
2. **一次只改一个缺陷。** 夹带两个修复，出问题无法定位，也没法做单点复测。
3. **复测只验这一个**，不顺带测别的。
4. **打回必须写原因**：现象、环境、复现步骤。不许只写"还是不行"。
5. **不许跳过复测进回归。** 单个 bug 没验过，回归结果不可信。

## 七、清零门禁（阶段 7 → 8）

**必须满足全部三条，才允许进入全量回归：**

- [ ] `state.yaml` 的 `open_bugs` 为空
- [ ] `07-bugs.md` 里没有「待修复」「待复测」「打回」状态的单子
- [ ] 每条已关闭缺陷都有测试填写的复测结论

任何一条不满足 → 停在阶段 7，不许往下走。

**回归门禁只有一个判定**：结论为「通过」，或结论为「有条件通过」且条件非空、用户显式确认并已写入 state，才允许上线；「不通过」、结论缺失或无法解析都直接退回。进入回归前 `pending_decisions` 必须为空，所有当前有效 A 必须已执行并在回归收尾时全部 `pass`。

## 八、角色隔离：三种执行模式

七个角色是**分开定义**的（职责、留档物、门禁都独立），但"分开定义"不等于"独立执行"。

如果是同一个模型在一次对话里轮换七个角色，角色是分开的，**脑子是同一个**。它会写代码时漏掉一条校验，做测试时同样想不起来——这叫同源盲区。

所以新增这一节，把三种强度写清楚，按场景选：

| 模式 | 做法 | 隔离强度 | 成本 | 适用 |
|---|---|---|---|---|
| **1 角色切换**（默认） | 同一对话内按专家文件切换身份，靠门禁和"必须写待验点"约束 | 弱，同源盲区仍在 | 低 | 小改动、快速验证 |
| **2 子代理隔离**（推荐） | 每个角色起独立上下文，**只传留档物，不传对话历史** | 中，上下文独立 | 中 | 正式跑一遍流程 |
| **3 换人 / 换模型** | 开发与测试由不同人或不同模型执行 | 强 | 高 | 高风险模块、上线前终验 |

### 模式 2 怎么执行

- 在 `state.yaml` 记录 `mode: 2`，并把开发、测试会话 ID 分别记入 `agent_sessions.developer`、`agent_sessions.tester`。
- 阶段 5 起开发子代理，输入只有：`04-tasks.md` + `03-arch.md` + `03-mapping.md` + `state.yaml` + 代码库，**不给需求讨论过程**。
- 阶段 6 起独立测试子代理，输入只有：`04-tasks.md` + `03-arch.md` + `03-mapping.md` + `02-prd.md` + `facts.md` + `state.yaml` + 代码本身，**不给开发日志中的实现理由和对话记录**。
- 阶段 7 恢复原 `developer` 会话；复测仍由原 `tester` 做。若平台无法恢复，明确记录并新建开发子代理，只传留档物与缺陷单，不得声称保留了原上下文。

模式 3 另需记录 `agent_sessions.final_reviewer`、`final_review_result` 和 `final_review_evidence`。独立终验可填 `human:<姓名>` 或 `model:<名称>`。

### 一条硬约束（三种模式都适用）

> **测试进场时，不许读开发的对话过程与实现理由。**

读了就会被说服——"他这么写是有原因的"。这是测试最容易失守的地方，而且失守时毫无察觉。

### 什么时候必须升级到模式 3

- 涉及金额、权限、状态机的关键改动
- 高风险模块的上线前终验（其他正式项目由模式 2 的独立测试上下文终验）
- 这个模块以前出过事故

触发以上任一项时暂停并让用户安排独立人员或模型；未实际完成独立终验，不得自称满足模式 3，也不得上线。

### 模式 1 的补偿机制

如果只能用模式 1，靠三样东西补：

1. **待验点必须由开发写**，且必须写"怎么验会失败"，不能只写"已验证"
2. **测试只照待验点和验收标准走**，不参考实现细节
3. **断点日志记下来**——每次"测试没抓到但后来暴露了"的，都是一条同源盲区的证据

## 九、决策点协议

### 必须停下来问的三类

1. **业务规则有歧义，且不同解释会导出不同的数据模型。**（例：超时以创建时间还是受理时间为准）
2. **技术选型存在实质分叉，且用户环境未知。**（例：私有化还是 SaaS、是否允许改表结构）
3. **改动不可逆或影响面无法自判。**（例：删字段、改协议版本、调整状态机）

### 不许问的三类

1. **能靠读代码、文档、配置确定的** —— 自己去读。
2. **行业有默认做法的** —— 按默认做，留档物里注明「按默认处理：……」。
3. **纯风格偏好**（命名、注释语言、目录结构）—— 跟随项目现状。

### 提问方式

- 一次最多 3 个问题，一轮问完。涉及**多角色或变长审批链**时允许到 4 个——那种场景三个问题确实不够。
- 每个问题给 2–4 个选项，标出推荐并附一句理由。
- 用结构化提问（`AskUserQuestion`），不要把选择埋在段落里。
- 用户答「你定」时按推荐执行，并记进 `decision_log`；只有真正未决的问题才能留在 `pending_decisions`。

## 十、事实源、断点日志与模板

- 事实源规则：`references/facts-source.md`
- 断点自查：`references/breakpoints.md`（阶段 2 查 B1、阶段 3 查 B2/B3、阶段 5 查 B4、阶段 6 查 B5、阶段 7 查 B6）
- 门禁：`references/gates.md`

模板（复制到 `.aiflow/` 后改名使用）：

| 模板 | 用于阶段 | 落地为 |
|---|---|---|
| `templates/state.yaml` | 0 起 | `.aiflow/state.yaml`（机器状态，随阶段更新） |
| `templates/intake.md` | 0 | `artifacts/00-intake.md` |
| `templates/research.md` | 1 | `artifacts/01-research.md` |
| `templates/prd.md` | 2 | `artifacts/02-prd.md` |
| — | 3 | `artifacts/03-arch.md`（**没有模板，形式由 PRD 决定**） |
| `templates/mapping.md` | 3 | `artifacts/03-mapping.md`（**唯一强制格式的产物**） |
| `templates/tasks.md` | 4 | `artifacts/04-tasks.md` |
| `templates/dev-log.md` | 5 | `artifacts/05-dev-log.md` |
| `templates/test-report.md` | 6 | `artifacts/06-test-report.md` |
| `templates/bugs.md` | 6–7 | `artifacts/07-bugs.md` |
| `templates/regression.md` | 8 | `artifacts/08-regression.md` |
| `templates/release.md` | 9 | `artifacts/09-release.md` |

事实源是**业务语义的唯一事实源**；架构、任务和测试产物是受控下游输入，不得与 facts 冲突。产出必须引用编号（R1、A3、T3）。

> **阶段 3 没有模板，这是有意的。** 架构方案的形状由 PRD 推导得出，不由文档结构决定。给模板等于预设结论，架构师就会照着填。唯一强制的是 `03-mapping.md`（验收标准 → 由哪条约束保证），因为后面三阶段都要反复查它。

## 十一、漂移控制

模型执行这套流程时，漂移是必然的：爱写的多写，不爱写的略过；这次三节，下次八节；同一概念换个说法。光靠"写的时候注意"没用——漂移发生时毫无察觉。

四种漂移，四种硬办法：

| 形态 | 表现 | 办法 | 能否自动 |
|---|---|---|---|
| **漏** | 14 条标准只落了 11 条 | 编号台账，分母是全集，差集就是漏 | ✅ 脚本 |
| **编** | 引用了不存在的编号 | 编号必须能在 facts 里找到 | ✅ 脚本 |
| **滑坡** | 产物结构忽大忽小 | 最小可检索单元（只规定必须能被找到，不规定骨架） | ⚠️ 半自动 |
| **失真** | 下游读出来跟你写的不是一回事 | 让下游**复述**，不是"读一遍说 ok" | ❌ 人工 |

### 每阶段收尾跑一次

```
python "<本 skill 目录>/scripts/check.py" "<项目目录>"
```

检查事实源定义、分产物覆盖、T/E 编号、任务完成状态、缺陷复测、验收执行、facts 版本、回归结论和发布终态。关键产物缺失、编号凭空编造、版本过期均为阻塞。

退出码：0 通过 / 1 有阻塞项 / 2 只有警告。**退出码不是 0 就不许进下一阶段。**

### 复述校验（脚本做不到的那部分）

阶段 3 收尾，让测试角色做两件事：

1. 用自己的话复述"这条验收标准靠什么保证"
2. 与方案原文对照

复述不出来，或者复述得比原文宽松，就是失真。**"读一遍说没问题"不算，那是走过场。**

## 十二、通用性要求

- skill 文件里**不许出现具体项目名**，示例用中性词或多行业轮换。
- `state.yaml` 的 `project` 由用户输入决定。
- 行业特有规则（客服 SLA、巡检超时、制造公差）只出现在用户填的事实源里。
- 换项目时 skill 一个字不改，只改 `.aiflow/` 下的内容。

## 十三、适用边界

**能处理**：一个业务对象、一条主流程（3–5 状态）、3–8 条可判定规则、用户能当场拍板。

**处理不了**：多系统集成（呼叫中心、支付、OCR）、规则还在探索期、要生产级（权限体系、高并发、安全审计）、已有系统小改。

遇到大词，**不拒绝也不硬吞**——在阶段 0 切成纵切，只做第一个。
