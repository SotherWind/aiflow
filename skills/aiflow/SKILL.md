# aiflow — AI 全流程交付工作流

## 一、激活与调用

| 指令 | 行为 |
|---|---|
| `/aiflow <一句话需求>` | 建流程，进阶段 0（澄清），**不直接进开发** |
| `/aiflow 继续` | 推进到下一阶段；不需要设计稿时自动跳过阶段 3 和阶段 7 |
| `/aiflow 状态` | 打印当前阶段、留档物、待确认、未解决问题、未关闭缺陷与走查问题单 |
| `/aiflow 跳到 <阶段号>` | 允许跳，但先补前一阶段的留档物检查，缺失就拒绝 |
| `/aiflow 回退 <阶段号>` | 回退，并把下游产物标记为失效 |
| `/aiflow 改 <变更描述>` | 走变更流程：先改事实源 → 算影响面 → 按编号重跑 → 已确认的产物重新确认（见 `references/change.md`） |

> ⚠️ 八个角色是**内部角色**，不是斜杠命令，不对外暴露。唯一入口是 `/aiflow`。

### 首次激活先初始化

1. 以用户当前项目为根目录；若 `.aiflow/` 已存在，读取状态并续跑，**不得覆盖**。`state.yaml` 没有 `flow_version: 2` 的旧项目，按 `README.md`「从旧版迁移」处理。
2. 新建 `.aiflow/artifacts/`；复制 `templates/state.yaml` 为 `.aiflow/state.yaml`、`templates/questions.md` 为 `.aiflow/questions.md`、`templates/intake.md` 为 `artifacts/00-intake.md`；新建 `.aiflow/breakpoint-log.md`。
3. 填写 `project`，保持 `stage: 0`、`facts_version: 0`，并在 `artifacts` 登记 `00-intake.md`。阶段 0 使用 facts v0，**此时不要求 `facts.md` 存在**。
4. 进入阶段 1 时复制 `templates/facts.md` 为 `.aiflow/facts.md`，从 v1 开始填写；每进入一个阶段，复制对应模板并先更新 `state.yaml`。
5. 每阶段收尾运行 `python "<本 skill 目录>/scripts/check.py" "<项目目录>"`。退出码必须为 0 才能推进；1 是阻塞，2 是仍有警告。

## 二、五条铁律

1. **一次只推进一个阶段。** 跳过的确认会在验收时连本带利还回来。
2. **没有留档物，这一阶段就不算完成。** 口头结论不算。
3. **判断不了必须问，不要替用户编。**
4. **必查项不等于必填项。** 每一节要求你做的是一次**判断**，不是填满表格。结论可以是「不适用」，但必须写明理由；**不允许空白跳过，也不允许为了填满而硬写**。
5. **要用户确认的节点，只认用户本人的明确确认。** 用户没回、回答含糊、AI 觉得"应该没问题"，都不算确认。

## 四、追问与确认

需求分析师、产品经理、体验设计师遇到不清楚的地方，都按 `references/grilling.md` 追问：把待决事项画成决策树，一轮问完当前能问的全部问题并给出推荐答案，答完重算，**问到没有未访问的分支为止**，不设题数上限。问题登记在 `.aiflow/questions.md`，每个阶段收尾时不得有「待问 / 待答复」。

要用户确认的节点按 `references/review.md` 走：交付 → 请用户确认 → 用户提了问题就照改、不清楚就追问 → 再交付，**循环到用户明确确认为止**。

| 确认点 | 阶段 | signoffs 键 | 确认什么 |
|---|---|---|---|
| 范围 | 0 | `scope` | 本轮做什么、不做什么 |
| 需求 | 1 | `requirement` | 规则都问清了，没有遗留问题 |
| PRD | 2 | `prd` | PRD 没问题，含要不要原型、要不要设计稿 |
| 产品原型 | 2 | `prototype` | 原型没问题；不需要时 `skipped` |
| 设计稿 | 3 | `design` | 设计稿没问题；不需要时 `skipped` |

确认记在产物的「用户确认」小节：确认结论、用户原话、确认时间。**用户原话只能来自用户本人的消息**；子代理接触不到用户，追问和确认只在主会话做。

## 五、阶段 0 是关口

用户说的大多是大词：「做一个企业智能客服」「做个数字化平台」。

阶段 0 做五件事：

1. **判断范围**：能用一个名词说清业务对象吗？规则能在 8 条以内吗？
2. **判断形态**（这一条决定后面的阶段长什么样）：

   | 形态 | 特征 | 本流程适配度 |
   |---|---|---|
   | **流程型** | 有状态流转、多角色、有先后 | 高，默认形态 |
   | **计算型** | 核心是算得对（金额、折扣、分账） | 中，要额外强调"边界值与精度"用例 |
   | **批处理型** | 定时跑、导入、对账、可重跑 | 中，任务要标 `JOB`，测试要测断点续跑 |
   | **并发型** | 存在同时写入的可能（抢库存、抢号、抢状态） | **阶段 0 只标线索，不下结论**，怎么处理交给架构师判断 |
   | **效果型** | 核心是产出质量（摘要好不好、推荐准不准、识别对不对） | **低，必须先降维**："好不好"不可判定，得换成"符合某条可判定的规则"才能开工 |

3. **标出风险线索，不下技术结论**：有同时写入的可能标「存在并发写入」，涉及金额、费率标「涉及数值精度」，定时、导入、对账标「批处理」。架构师看到线索后可以判断"本项目不涉及"，但必须写下理由。**"不会"是允许的答案，"没判断"不允许。**
4. **切纵切**：拆成 4–8 个纵切，只选第一个开工。
5. **追问范围并请用户确认**：影响范围和数据模型的问题按决策树逐轮问完，没有问题就写「无」，不得硬凑；然后把「本轮做 / 本轮不做」和「按默认处理」清单交用户确认。

产物 `00-intake.md` 里必须有两句：

> 本轮做：<纵切名>　｜　本轮不做：<其余纵切列表>
> 形态：<流程型 / 计算型 / 批处理型 / 并发型 / 效果型>　｜　风险线索：<并发写入 / 数值精度 / 批处理 / 无>

缺任一句，或者用户没有确认范围，不许进阶段 1。

## 六、产品原型、设计稿与设计走查

**要不要**：产品经理在 PRD 的「交付形态判断」里写明要不要原型、要不要设计稿及理由，用户确认 PRD 时一起确认，同步到 `state.yaml` 的 `prototype_required`、`design_required`。两者互相独立，判断依据见 `experts/pm.md` 与 `experts/ux.md`。需要其中任何一个时，再按 `references/design-system.md` 确定设计规范，记进 `.aiflow/design-system.md`，原型、设计稿、前端开发都用它。

**产品原型**（阶段 2，PRD 确认之后）：页面编号 `P1..Pn`，每页写清服务哪几条 A、字段、操作、状态、跳转。做到中保真（规范见 `references/prototype.md`）：用组件库的真实组件、真实文案和功能色，有全局说明、页面流程图、角色 × 状态矩阵，每页带编号标注；有设计规范时用规范的令牌，没有时品牌视觉留给设计稿。默认用 `templates/prototype-kit/` 出 HTML，放在 `.aiflow/prototype/`，样式内联，另导出 PNG。

**设计稿**（阶段 3）：体验设计师按 PRD 和原型逐页出稿，每页画全状态；交互标注编号 `I1..In`；走查点清单编号 `W1..Wn`。走查点随设计稿一起确认后冻结，前端开发之前就公开。默认出 HTML 设计稿，放在 `.aiflow/design/`。

**设计走查**（阶段 7，前端开发完之后）：体验设计师在浏览器里打开页面，逐个走查点判定。

- 还原度 = 通过的走查点 ÷ 全部走查点，每个走查点取最近一轮的结果
- **≥ 90% 且关键项全部通过才算通过**。关键项：页面存在且可达、交互标注逐条实现、空 / 加载 / 出错状态存在
- 不达标的点逐条开成走查问题单 `UX-n` 派给前端；前端改完改成「待复查」并通知体验设计师；体验设计师复查后重算还原度，循环到通过为止
- 通过时仍未达标的非关键点记为「遗留」，写进走查结论

阶段 9 前端修缺陷改到已走查的页面时，体验设计师复查受影响的走查点，回归报告写「设计还原复核」。

## 七、任务编号是主键

阶段 5 拆出的每个任务都有编号 `T1..Tn`，并带类型：`FE`、`BE` 或 `JOB`；JOB 由后端开发负责。有原型或设计稿时，每个页面 `P` 至少落到一个 FE 任务。

粒度标准：**一个人能独立开发完、另一个人能独立验收的单元。** 通常对应一个接口或一个页面。

任务编号贯穿全流程：

- 开发日志按任务记：`T3(BE) 完成`
- 测试报告按任务测：`T3 通过 / T5 失败`
- 缺陷挂任务，**并按任务类型自动派给对应开发**：`BUG-2 · 关联 T5(FE) · 派给前端`
- 回归按任务推范围：`受影响任务：T5、T7`

## 八、缺陷往返协议（阶段 9）

```
测试开单（挂任务 + 派单） → 状态「待修复」
    ↓
对应开发修复 → 填「修复说明 + 待验点」 → 状态「待复测」
    ↓
测试复测 → 通过「已关闭」 ／ 不通过「打回」并写清原因
    ↓
打回 → 回到原开发，重新进入循环
```

五条硬规矩：

1. **不许口头传。** 修了什么、让验什么，必须写在单子上。
2. **一次只改一个缺陷。** 夹带两个修复，出问题无法定位，也没法做单点复测。
3. **复测只验这一个**，不顺带测别的。
4. **打回必须写原因**：现象、环境、复现步骤。不许只写"还是不行"。
5. **不许跳过复测进回归。** 单个 bug 没验过，回归结果不可信。

阶段 7 的走查问题单走同一个循环，复查人是体验设计师。

## 九、清零门禁（阶段 9 → 10）

**必须满足全部三条，才允许进入全量回归：**

- [ ] `state.yaml` 的 `open_bugs` 为空
- [ ] `09-bugs.md` 里没有「待修复」「待复测」「打回」状态的单子
- [ ] 每条已关闭缺陷都有测试填写的复测结论

任何一条不满足 → 停在阶段 9，不许往下走。

**回归门禁只有一个判定**：结论为「通过」，或结论为「有条件通过」且条件非空、用户显式确认并已写入 state，才允许上线；「不通过」、结论缺失或无法解析都直接退回。进入回归前 `pending_decisions` 必须为空，所有当前有效 A 必须已执行并在回归收尾时全部 `pass`。

## 十、角色隔离：三种执行模式

八个角色是**分开定义**的（职责、留档物、门禁都独立），但"分开定义"不等于"独立执行"。同一个模型在一次对话里轮换八个角色，角色是分开的，**脑子是同一个**：写代码时漏掉一条校验，做测试时同样想不起来。这叫同源盲区。

| 模式 | 做法 | 隔离强度 | 成本 | 适用 |
|---|---|---|---|---|
| **1 角色切换**（默认） | 同一对话内按专家文件切换身份，靠门禁和"必须写待验点"约束 | 弱，同源盲区仍在 | 低 | 小改动、快速验证 |
| **2 子代理隔离**（推荐） | 每个角色起独立上下文，**只传留档物，不传对话历史** | 中，上下文独立 | 中 | 正式跑一遍流程 |
| **3 换人 / 换模型** | 开发与测试由不同人或不同模型执行 | 强 | 高 | 高风险模块、上线前终验 |

### 模式 2 怎么执行

- 在 `state.yaml` 记录 `mode: 2`，把开发、设计、测试会话 ID 分别记入 `agent_sessions.developer`、`agent_sessions.designer`、`agent_sessions.tester`。
- 阶段 0–3 的追问和确认在主会话做，子代理接触不到用户。
- 阶段 6 起开发子代理，输入只有：`05-tasks.md` + `04-arch.md` + `04-mapping.md` + 原型与设计稿（如有）+ `state.yaml` + 代码库，**不给需求讨论过程**。
- 阶段 7 的走查由设计会话做，不由开发会话自查。
- 阶段 8 起独立测试子代理，输入只有：`05-tasks.md` + `04-arch.md` + `04-mapping.md` + `02-prd.md` + `facts.md` + `state.yaml` + 代码本身，**不给开发日志中的实现理由和对话记录**。
- 阶段 9 恢复原 `developer` 会话；复测仍由原 `tester` 做。若平台无法恢复，明确记录并新建开发子代理，只传留档物与缺陷单，不得声称保留了原上下文。

模式 3 另需记录 `agent_sessions.final_reviewer`、`final_review_result` 和 `final_review_evidence`。独立终验可填 `human:<姓名>` 或 `model:<名称>`。

### 一条硬约束（三种模式都适用）

> **测试和设计走查进场时，不许读开发的对话过程与实现理由。**

读了就会被说服："他这么写是有原因的"。这是验收最容易失守的地方，而且失守时毫无察觉。

### 什么时候必须升级到模式 3

- 涉及金额、权限、状态机的关键改动
- 高风险模块的上线前终验（其他正式项目由模式 2 的独立测试上下文终验）
- 这个模块以前出过事故

触发以上任一项时暂停并让用户安排独立人员或模型；未实际完成独立终验，不得自称满足模式 3，也不得上线。

### 模式 1 的补偿机制

1. **待验点必须由开发写**，且必须写"怎么验会失败"，不能只写"已验证"
2. **测试只照待验点和验收标准走**，不参考实现细节
3. **断点日志记下来**：每次"测试没抓到但后来暴露了"的，都是一条同源盲区的证据

## 十一、决策点协议

### 必须停下来问的三类

1. **业务规则有歧义，且不同解释会导出不同的数据模型。**（例：超时以创建时间还是受理时间为准）
2. **技术选型存在实质分叉，且用户环境未知。**（例：私有化还是 SaaS、是否允许改表结构）
3. **改动不可逆或影响面无法自判。**（例：删字段、改协议版本、调整状态机）

### 不许问的三类

1. **能靠读代码、文档、配置确定的**：自己去读。
2. **行业有默认做法的**：按默认做，留档物里注明「按默认处理：……」，让用户看得见、能反对。
3. **纯风格偏好**（命名、注释语言、目录结构）：跟随项目现状。

### 提问方式

- 按 `references/grilling.md`：一轮问完当前前沿的全部问题，**不设题数上限**，也不为少问而替用户默认。
- 每个问题给 2–4 个选项，标出推荐并附一句理由，写明影响哪条 R、A、哪个页面或数据模型。
- 用结构化提问（`AskUserQuestion`），一次装不下就分几次连续问完，不要把选择埋在段落里。
- 用户答「你定」时按推荐执行，在 `questions.md` 记「按推荐」和用户原话。

## 十三、漂移控制

模型执行这套流程时，漂移是必然的：爱写的多写，不爱写的略过；这次三节，下次八节；同一概念换个说法。光靠"写的时候注意"没用，漂移发生时毫无察觉。

| 形态 | 表现 | 办法 | 能否自动 |
|---|---|---|---|
| **漏** | 14 条标准只落了 11 条 | 编号台账，分母是全集，差集就是漏 | ✅ 脚本 |
| **编** | 引用了不存在的编号 | 编号必须能在 facts 和产物里找到定义 | ✅ 脚本 |
| **滑坡** | 产物结构忽大忽小 | 最小可检索单元（只规定必须能被找到，不规定骨架） | ⚠️ 半自动 |
| **失真** | 下游读出来跟你写的不是一回事 | 让下游**复述**，不是"读一遍说 ok" | ❌ 人工 |

### 每阶段收尾跑一次

```
python "<本 skill 目录>/scripts/check.py" "<项目目录>"
```

检查用户确认、问题台账、设计规范来源、事实源定义、分产物覆盖、原型与设计稿页面、走查点与还原度、T/E 编号、任务完成状态、缺陷复测、验收执行、facts 版本、回归结论和发布终态。关键产物缺失、编号凭空编造、版本过期、确认缺失均为阻塞。

退出码：0 通过 / 1 有阻塞项 / 2 只有警告。**退出码不是 0 就不许进下一阶段。**

脚本能查「用户确认」有没有填，查不了用户原话是不是用户本人说的。这一条靠第五条铁律。

### 复述校验（脚本做不到的那部分）

阶段 4 收尾，让测试角色做两件事：

1. 用自己的话复述"这条验收标准靠什么保证"
2. 与方案原文对照

复述不出来，或者复述得比原文宽松，就是失真。**"读一遍说没问题"不算，那是走过场。**

## 十四、通用性要求

- skill 文件里**不许出现具体项目名**，示例用中性词或多行业轮换。
- `state.yaml` 的 `project` 由用户输入决定。
- 行业特有规则（客服 SLA、巡检超时、制造公差）只出现在用户填的事实源里。
- 换项目时 skill 一个字不改，只改 `.aiflow/` 下的内容。

## 十五、适用边界

**能处理**：一个业务对象、一条主流程（3–5 状态）、3–8 条可判定规则、用户能当场拍板。

**处理不了**：多系统集成（呼叫中心、支付、OCR）、规则还在探索期、要生产级（权限体系、高并发、安全审计）、已有系统小改。

遇到大词，**不拒绝也不硬吞**：在阶段 0 切成纵切，只做第一个。
