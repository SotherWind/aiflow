# 主智能体、阶段执行协调器与专业子智能体

新项目默认模式 2。模式 2/3 按下表确定每个阶段的执行方式，主会话不逐次自行判断：单角色阶段由**主智能体直接派独立专业子智能体**；多角色往返的阶段由**主智能体 → 本阶段独立执行协调器 → 独立专业子智能体**。协调器负责执行编排，不是第九个专业角色；用户始终只和主会话沟通。

| 执行方式 | 阶段 | 说明 |
|---|---|---|
| 主智能体直接派 | 0、1、2、5、8、10、11 | 本阶段只有一个专业角色（分析师、产品经理、架构师、测试或运维），加协调器只多一跳转发 |
| 本阶段执行协调器 | 3、4、6、7、9 | 出稿与独立评审、架构与测试试读、前后端开发、走查往返、修复与复测，需要在角色之间来回派工 |

协调器阶段遇到原生嵌套确实不可用时，才改为主智能体直接派，按下文记录原因。下文的「派工方」指本阶段实际派角色的一方：直接派阶段是主智能体，协调器阶段是协调器；角色的结果交回派工方，修改也由派工方续派。

## 调度方式与生命周期

每进入一个需要执行的阶段，主智能体按上表实际调用原生子智能体工具：直接派阶段新建所需的专业子智能体；协调器阶段先新建该阶段的独立执行协调器，再由协调器按角色新建本阶段所需的专业子智能体。每次新建都使用独立上下文，支持 `fork_turns` 时设为 `none`，只传本次交接输入，不创建侧栏聊天。模型沿用当前环境与用户配置。

同阶段的澄清、修改、失败重试和后续任务由本阶段派工方续派，同角色可复用本阶段自己的工作会话，但每次都须实际发送新任务并等待返回。跨阶段、回退到另一阶段或重新进场重做时，新建所需角色，协调器阶段同时新建协调器；例如阶段 0、1 分别新建分析师，阶段 4、5 分别新建架构师。旧 ID 和读过专家文件都不算本次派工，也不能把某角色上下文改作另一角色。

按需启动并按依赖排队；前后端契约明确、文件范围不重叠时才并行。名额不足时串行，完成结果留存后按平台能力释放空闲会话，不因并发暂满改由主控或协调器代做专业工作。

协调器阶段只有在原生嵌套子智能体确实不可用（如实际工具不支持、深度限制或调用被禁止）时，才由主智能体直接派独立专业子智能体；向用户说明具体限制，并记录 `strategy: direct` 与实际依据，不声称存在协调器。独立工作子智能体也不可用、无法隔离或用户选择单会话时，用模式 1 如实角色切换，保留确认点与独立验收要求；用户要求必须独立的部分不能自行降级。已有项目沿用实际模式，能力或模式变化保留历史，不因本次交接补造过去的执行。

## 三层职责与写入边界

- **主智能体**：持有用户需求和全局共识，按 `clarification.md` 优先交互式提问、受限时用文字；主持澄清、展示产物、接收真实反馈与确认、作最终阶段验收。确定本阶段目标、有效输入、授权与总写入范围。直接派阶段由主智能体自己承担派工、追踪返回与汇总；各阶段收尾都由主智能体亲自运行 `check.py`。只有主智能体写 `state.yaml`、`questions.md`、所有用户确认字段和阶段状态；专业文件中的“同步状态 / 请用户确认”均按此边界执行。
- **执行协调器**：在授权范围内拆分派工、处理依赖、追踪返回、安排重试与独立评审、阅读详细结果、汇总日志。将需要用户决定的问题、证据与推荐交主控，收到真实决定后再派相关任务。协调器不直接面向用户，不写主控专属文件或确认字段，不代替专业产出或独立评审，也不宣布阶段已获确认或签收。
- **专业子智能体**：只执行自己的专业任务，使用当前有效且与任务有关的输入，在指定文件范围内落专业产物；向派工方返回结果、真实检查证据、待决事项与状态更新建议。评审、测试和走查保持独立，不接收出稿或开发过程的推理与辩护。

无论经协调器还是由角色直接交回，主控通常只接收**任务状态、产物位置、检查结论及证据索引、未决事项、必要控制更新和真实 ID**；完整产物、失败尝试和原始测试日志留在对应文件或执行上下文中。主控据摘要验收与组织用户评审，不例行重读整套产物；证据缺失、矛盾或验收需要时可定点查看相关片段。

阶段 0 由主控直接派分析师查证并展开决策树，在对话中回传；主控同时推进已能问的问题，不等整份报告。共识收口前不创建任何初始 `.aiflow/` 文件，包括状态、台账、执行日志或占位产物，ID 与过程证据暂留会话。收口后主控建目录并落状态、台账，再向分析师派产物编写任务；用户明确要求中途保存时按澄清协议保存真实未完成进度。

## 八个角色怎样交接

派工方每次派工都给本调度协议、对应专家文件的绝对路径、项目根目录和必要参考文件，写清阶段、目标、有效输入、相关用户决定、可写文件与返回要求。以下输入均限当前有效版本；不传整段聊天、其他角色推理或无关文件，history 和失效产物只用于指定的追溯工作。澄清未收口时仅派查证与分析，产物任务明确共识已收口。

| 角色 / 会话键 | 阶段 | 主要输入 | 返回或负责的产出 |
|---|---|---|---|
| 需求分析师 `analyst` | 0–1 | 用户原始需求、相关答复摘要与原话、已有资料；阶段 1 加已确认 intake | 证据、根问题、推荐与范围建议；收口后编写 intake、research、业务规则 R |
| 产品经理 `pm` | 2 | intake、research、facts、相关已确认决定及规范 | PRD、验收 A、交付形态判断；PRD 确认后需要时制作原型 |
| 体验设计师 `designer` | 3、7，9 按需复查 | PRD、原型、视觉要求、设计规范；图片确认后加确认版图片与反馈；走查时加已确认 HTML 设计 | 先生成/编辑设计图片，主会话取得图片确认后再制作 HTML、截图核对与自检；后续走查和设计还原复核 |
| 技术架构师 `architect` | 4–5 | PRD、facts、原型与设计、代码现状、技术要求及开发规范 | 选型建议；收口后架构、契约映射与选型文件；阶段 5 拆任务 |
| 前端开发 `fe` | 6、7、9 | FE 任务、架构、映射、锁定技术栈、前端规范、原型与设计、相关代码及问题单 | 分配范围内的前端代码、实际检查证据、待验点与修复结果 |
| 后端开发 `be` | 6、9 | BE/JOB 任务、架构、映射、锁定技术栈、后端规范、相关代码及问题单 | 后端与 JOB 代码、实际检查证据、待验点与修复结果 |
| 测试工程师 `tester` | 4 试读，8–10 | PRD、facts、架构、映射、任务、锁定技术栈及规范、代码；复测加缺陷与历史测试证据 | 阶段 4 可验收性反馈；测试报告、缺陷单、逐轮复测与全量回归 |
| 运维工程师 `operator` | 11 | 已通过的回归与缺陷记录、锁定技术栈、架构、变更清单、目标环境及实际操作授权 | 发布与回滚方案、环境核对、获授权后的执行和观察证据 |

两个按条件派出的角色也进入本阶段必需名单：阶段 7 有「已关闭」的走查问题单时要求 `fe`，因为关单前要由前端改成「待复查」，只有「遗留」的单子不算；阶段 9 有 FE 缺陷单的「待验点」列了走查点编号时要求 `designer` 复查，引用未定义的走查点会被拦下。条件满足后与固定角色同样检查：`agent_sessions` 有本角色 ID，`stage_dispatch` 有本阶段完成依据，有 `session_log` 时记在本次执行下。

角色需要用户判断时，经派工方返回问题、证据与推荐，由主控提问；暂停依赖答案的工作，其他独立工作可继续。协调器与角色均不调用面向用户的提问工具或模拟答复。具体阶段工作仍由专家文件约束；接到发布任务不意味着新增生产操作授权。

阶段 3 由协调器分次派工：实际生图与编辑 → 主控展示并取得图片确认 → 设计师制作 HTML、逐页面及对应视口浏览器截图核对 → 独立设计评审 → 主控展示并取得最终确认。生图能力仅主控可用时，设计师经协调器提供最小可执行提示词、参考图与修改要求，主控代调实际工具，把真实结果经协调器交回设计师。图片确认前不派 HTML 任务，也不要求最终角色完成证据或门禁先通过。

最终 HTML 交付前，协调器另起 `design_reviewer`，只交确认图片、HTML、真实截图、PRD 与必要设计依据；其 ID 与出稿者、协调器及其他角色不同。评审问题由设计师修改，再由评审者复核，协调器不代评。模式 3 的 `final_reviewer` 同样独立于协调器和所有执行角色。

## 执行回收与阶段验收

1. 派工方等待各角色实际返回，检查产物位置、改动范围、证据和未决事项，处理失败、修复与复测。没有返回或中断就保留未完成；同阶段 PRD → 原型、图片 → HTML、修复 → 复测都须真正续派，不能拿之前一次完成顶替。
2. 协调器阶段由协调器汇总共享 `06-dev-log.md`、`breakpoint-log.md` 与详细执行记录；直接派阶段由角色在指定文件范围内自行记录，主控不代写详细日志。其他共享文件指定单一写入者或串行交接。缺陷按“测试开单 → 对应 `fe` / `be` 修复 → `tester` 复测”流转，页面变化交本阶段 `designer` 复查。记录保留失败历史；汇总记录不代做修复或验收。
3. 协调器阶段由协调器向主控回传操作结果：任务状态、产物路径、检查结论和证据索引、未决事项、建议写入的状态值、实际 ID 与派工/完成依据。这个返回是 `stage_execution.handoff` 的依据，表示执行交接，不表示阶段已签收。直接派阶段由角色按同样内容直接交回主控，不记 `handoff`。需要澄清或用户评审时只返回当前真实进度，不要求最终完成证据。
4. 主控据此写 `agent_sessions`、`stage_dispatch`、`stage_execution` 及其他机器状态；由主控完成必要的用户展示、提问与确认，并亲自写台账和确认字段。需要修改就将反馈交回派工方；新的执行使旧完成证据失效时先清除对应项。
5. 主控落档后，亲自对已持久化状态运行 `check.py`，据退出码、证据位置、阻塞摘要和真实用户确认作最终验收。退出码 0 才可推进，但脚本通过或角色、协调器“任务完成”都不能代替主控签收。需要专业修改的阻塞项交回派工方，修改后重新落档、重新检查。

该顺序避免门禁依赖尚未写入的自身交接证据。访谈未收口、图片待评审时，保留相应待完成状态，不提前要求正式产物、最终派工返回、协调器完成交接或收尾门禁。直接派阶段由主控承担上述编排与落档，专业工作仍交独立角色。

## 执行记录与身份

以下记录由主控按实际结果写入，首次项目仍在澄清收口后才建文件。进入新阶段或重做时先归档旧执行记录，再重置本阶段记录（`session_log` 只追加、不重置）；跳过的阶段不需要协调器或专业派工，归档后移除当前操作记录，不能把上阶段记录带到跳过阶段。

`agent_sessions` 按上表键保存各角色最近一次实际返回的 ID，需要独立评审时另记 `design_reviewer` / `final_reviewer`；同阶段替换会话时，派工方先记旧 ID、新 ID、原因和时间，主控再更新。不同专业角色与评审者的 ID 必须不同。旧 `developer` 仅保留历史身份，不能满足本次 `fe` 或 `be` 的派工；前后端仍分别新建独立上下文。ID、模式或策略变化记入 `breakpoint-log.md`，不声称已丢失的上下文仍存在。

`session_log` 是只追加的派工会话台账，用来查出换阶段沿用旧会话。每条写成 `"<执行序号> <阶段> <角色> <会话 ID>"`，角色为 `coordinator` 或上表的角色键。每次进入、回退或重做阶段，执行序号取台账已有最大值 + 1；本阶段派出的协调器和每个角色拿到实际 ID 后各追加一条，同阶段替换的会话也记在同一序号下。旧条目不删不改。平台按任务名生成会话 ID 时，任务名带上执行序号，避免新会话与旧会话同名。门禁要求本阶段需要的角色、`stage_dispatch` 中有完成依据的角色以及 `stage_execution` 记录的协调器都记在最新一次执行下，同一个会话 ID 只能出现在一次执行、一个角色中。旧项目没有台账时按兼容放行。

`stage_dispatch` 保持**一层映射**：`stage: N` 加本阶段已完成角色的字符串证据，例如 `analyst: "本阶段实际任务调用 …；完成返回 …；产物 …"`。重置时只留当前 `stage`；同阶段续派角色前移除该角色旧完成项，收到实际新结果再填。不能嵌套成角色对象，也不能只填旧 ID 或上一阶段结果。

可选顶层 `stage_execution` 也是一层映射，记录当前阶段的执行策略：

```yaml
stage_execution:
  stage: 4
  strategy: coordinated
  coordinator: "<原生工具实际返回的本阶段协调器 ID>"
  handoff: "<主控本阶段派工调用 + 协调器操作结果返回的实际引用或证据>"
```

`stage` 必须与当前阶段相同；`coordinator` 不得与任一专业角色、评审者或历史 `developer` 身份相同。模板的空值只表示尚未完成记录，不证明协调执行。`handoff` 不包含未来门禁或用户签收的伪造结论；主控先记录这次操作交接，再亲自检查已落档状态。

主控直接派工时，记录 `stage: N`、`strategy: direct`、`fallback_reason: "<直接派工的原因>"`：单角色阶段写「单角色阶段」，协调器阶段写实际的原生嵌套限制与证据。字段名为兼容沿用，不表示兜底；`coordinator` / `handoff` 省略或留空。旧项目缺少 `stage_execution` 时兼容为旧直接派工记录，不证明已有协调器；新执行或续跑交接记录实际策略，只补本次证据。

检查器只验证记录形状、身份和阶段的一致性，不核对执行方式是否符合上面的阶段执行表，并按 `session_log` 查出跨执行复用的会话；不能证明原生调用发生、上下文独立、台账 ID、证据或用户确认真实，同一阶段重做却沿用原执行序号时也查不出；这些仍由实际工具返回与产物证据支持。模式 1 不能凭这些字段声称独立执行或独立验收。
