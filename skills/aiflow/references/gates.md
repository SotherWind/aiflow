# 阶段门禁检查表

每阶段收尾前逐条自检。**任一条不通过，不许进入下一阶段。**

带「用户确认」的阶段，按 `references/review.md` 走；追问按 `references/clarification.md` 走。

**先澄清、后留档、再评审。** 以下只用于阶段收尾。新项目访谈期间无需文件；已有项目标记 `clarification: pending` 后继续对话，收口后统一整理记录和产物，再检查门禁。

## 阶段 0 · 需求澄清（需求分析师）→ `00-intake.md`

- [ ] 能用**一个名词**说清本轮的业务对象
- [ ] 按 `references/discovery.md` 展开产品决策树并反查核心路径；影响本轮范围的根问题已有依据，后续细化建立在已知边界上
- [ ] 产品目标、形态与期望能力已有依据，和本轮交付范围分开记录；多选需求未被改成单选或静默删除
- [ ] 范围过大时已拆成候选纵切，首个交付纵切及其配套能力由用户确认；范围足够小则不硬拆
- [ ] 有一句明确的：`本轮做：X ｜ 本轮不做：Y、Z、W`
- [ ] 有形态判断（流程型 / 计算型 / 批处理型 / 并发型 / 效果型）
- [ ] 有一句明确的：`风险线索：<并发写入 / 数值精度 / 批处理 / 无>`
- [ ] 风险线索只标不问结论，**没有在阶段 0 拍板技术方案**
- [ ] 当前可独立回答的问题已问，后置项有真实依赖；没有用固定题数、只看数据模型或台账清空代替查漏，推荐没有依赖未经确认的用途和约束
- [ ] 影响范围的问题按决策树逐轮问完，`questions.md` 里没有「待问 / 待答复」；没有问题时写「无」，不得硬凑
- [ ] **用户确认了范围**：`00-intake.md` 有用户确认，`signoffs.scope: confirmed`

- [ ] 相关核心任务的实际做法、值得参考的机制、适用条件与复用成本已比较，采用或不采用的理由与本轮问题和用户决定有关联
