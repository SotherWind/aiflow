# 阶段门禁检查表

每阶段收尾前逐条自检。**任一条不通过，不许进入下一阶段。**

## 阶段 0 · 需求澄清（需求分析师）→ `00-intake.md`

- [ ] 能用**一个名词**说清本轮的业务对象
- [ ] 大词已拆成 4–8 个纵切，且**只选第一个**
- [ ] 有一句明确的：`本轮做：X ｜ 本轮不做：Y、Z、W`
- [ ] 有形态判断（流程型 / 计算型 / 批处理型 / 并发型 / 效果型）
- [ ] 有一句明确的：`风险线索：<并发写入 / 数值精度 / 批处理 / 无>`
- [ ] 风险线索只标不问结论，**没有在阶段 0 拍板技术方案**
- [ ] 提了最多 3 个"不问清就没法定数据模型"的问题；没有阻塞问题就明确写「无」，不得硬凑
- [ ] **已停下等回答或范围确认**，没有自问自答

## 阶段 1 · 需求调研（需求分析师）→ `01-research.md`

- [ ] 写清现状：现在这件事怎么做的（人工 / 旧系统 / 没有）
- [ ] 写清约束：期限、已有系统、必须对接的东西
- [ ] 参考了至少一份同类做法，并写了"我们不照抄哪一点"
- [ ] 列出"没搞清的问题"，没假装都清楚

## 阶段 2 · PRD（产品经理）→ `02-prd.md`

- [ ] 每条验收标准都能写出至少一个失败用例
- [ ] 每条都引用了 R 编号
- [ ] 状态机完整，含"到点自动发生"的动作
- [ ] 非功能要求是具体数字
- [ ] 明确写了**不做什么**
- [ ] 跑过断点自查 B1

## 阶段 3 · 技术架构（技术架构师）→ `03-arch.md`

- [ ] **四问都有答案**：A 成立物理上要求什么 / 在哪一层保证 / 有无并发写 / 失败怎么表现
- [ ] 每条验收标准落到「由哪条约束保证」，而不是「写在某个函数里」
- [ ] 能放数据层的约束没有放在应用层（唯一索引、非空、条件更新）
- [ ] **技术栈可行性校验过**：每条关键约束需要的机制，在选定选型里真实存在；给不了的已换选型或记为技术债
- [ ] 有并行分支的流程，用了依赖图 + 推进条件，没有硬压成单线状态机
- [ ] 架构产物只包含推导得出的内容，没有为凑整齐补的空章节
- [ ] 五样信息可定位：数据怎么存 / 每条 A 由哪条约束保证 / 有无并发写 / 失败怎么表现 / 做什么与不做什么
- [ ] **由测试角色试读一遍**：按上面的五样去方案里找，任意一样找不到，退回重写
- [ ] 每条验收标准都有落点（字段/校验/任务）
- [ ] 映射表没有「无对应」，且没有虚构尚未产生的 T/E 编号
- [ ] 数据模型能支撑全部状态流转，不需要二次改表
- [ ] 「到点自动发生」的规则配了定时任务 + 幂等
- [ ] 错误码统一成表
- [ ] **并发问题做了判断并留痕**：结论为「存在」→ 每个共享状态都有策略与落点；结论为「不存在」→ 写了理由
- [ ] 若判定存在并发写：每处「先查后改」都回答了"两次查之间被改了怎么办"
- [ ] 若判定存在并发写：每处共享状态都有数据库约束、原子更新、锁或串行化等底层机制兜底；唯一性场景用唯一约束，不把应用层 if 当唯一保障
- [ ] 跑过断点自查 B2、B3

## 阶段 4 · 任务拆分（技术架构师）→ `04-tasks.md`

- [ ] 每个任务有编号 `T1..Tn`、类型 `FE`/`BE`/`JOB`、验收标准、依赖、测试要点
- [ ] 批处理与定时任务标成了 `JOB`，没有混进 `BE`
- [ ] 每个任务都是"一人能独立开发、另一人能独立验收"的颗粒
- [ ] 前几个任务能串成一条可跑通的主流程
- [ ] 风险任务（状态机、定时任务、迁移）排在前列
- [ ] 标了可并行的任务
- [ ] 已在 `03-mapping.md` 回填真实 T 编号；E 留到阶段 6 回填

## 阶段 5 · 开发（前端 / 后端）→ 代码 + `05-dev-log.md`

- [ ] 每个任务在日志里有：编号、类型、状态、涉及文件、测试要点
- [ ] `state.yaml.task_status` 覆盖全部 T，且进入阶段 6 前全部为 `done`；部分完成或未开始不得带过去
- [ ] 前端字段名与后端契约完全一致
- [ ] 服务端校验齐全（不只依赖前端）
- [ ] 状态变更落库且可追溯；定时任务有幂等
- [ ] 测试断言能读出对应验收标准，失败路径 ≥ 30%
- [ ] 跑过断点自查 B4

## 阶段 6 · 测试（测试工程师）→ `06-test-report.md`

- [ ] **每个任务**都有独立结论；未开始不是可接受的测试结论
- [ ] 每个任务的失败路径用例 ≥ 三分之一
- [ ] 用例有 E 编号并带验收标准编号；已在映射表回填 E
- [ ] 每条当前有效 A 至少一条已执行用例，`acceptance_results` 有 `pass/fail` 结果；`uncovered` 阻塞
- [ ] 不通过的任务都开了缺陷单，**且已派给对应开发**（FE→前端，BE/JOB→后端）
- [ ] `JOB` 任务额外测了三类：部分失败、断点续跑、重复执行幂等
- [ ] 架构文档判定「存在并发写」时，每个共享状态都有并发正确性用例（同时发起，断言最终值与成功次数，不是压测）
- [ ] 未覆盖项已补测，或通过 facts 变更移出本轮；不得只写原因放行
- [ ] 跑过断点自查 B5

## 阶段 7 · 缺陷修复与复测（开发 ⇄ 测试）→ `07-bugs.md`

- [ ] 每条缺陷有：关联任务、归属（FE/BE）、现象、复现、根因、影响面
- [ ] 修复是最小改动，一次只修一个
- [ ] 每条都有「修复说明 + 待验点」
- [ ] 每条都有测试的**复测结论**（没有口头通过）
- [ ] 打回的单都写了原因（现象/环境/复现）
- [ ] 跑过断点自查 B6

**清零门禁（进入阶段 8 的硬条件）**

- [ ] `state.yaml` 的 `open_bugs` 为空
- [ ] `07-bugs.md` 没有「待修复」「待复测」「打回」状态
- [ ] 每条已关闭缺陷都有复测结论

> 三条全满足才能进阶段 8。**不许带 bug 进回归。**

## 阶段 8 · 全量回归（测试工程师）→ `08-regression.md`

- [ ] 回归范围从已关闭缺陷的「受影响任务」推导而来，有过程
- [ ] 主流程全跑一遍，不管有没有被影响
- [ ] **所有当前有效 A 都有执行结果**；主流程和影响面不能替代全量验收覆盖
- [ ] `acceptance_results` 中所有当前有效 A 均为 `pass`，无 `uncovered`
- [ ] `pending_decisions` 为空
- [ ] 结论明确：通过 / 有条件通过（列条件）/ 不通过（列阻塞项），并与 state 一致

**上线门禁（进入阶段 9 的硬条件，只有两种可放行路径）**

- [ ] 「通过」；或「有条件通过」且条件非空、用户已显式确认并记录
- [ ] 「不通过」一律退回；任何缺失或无法解析的结论也退回

## 阶段 9 · 上线（运维工程师）→ `09-release.md`

- [ ] 变更清单完整（代码、配置、数据、依赖）
- [ ] 回滚方案是可执行步骤，不是"回滚到上一版"
- [ ] 回滚方案在测试环境走过一次
- [ ] 上线检查表逐项可勾选
- [ ] 数据变更说明了是否可逆、备份在哪
- [ ] `09-release.md` 已填写实际执行结果、证据和观察窗结论
- [ ] `release_status: verified`；`planned/deployed` 尚未完成，`rolled_back` 不算上线成功

## 通用门禁（每阶段都查）

- [ ] 跑过 `python "<本 skill 目录>/scripts/check.py" "<项目目录>"`，退出码为 **0**；1 和 2 都不得推进
- [ ] 必需产物存在且非空；缺产物是阻塞，不是警告
- [ ] 阶段 1 及之后的产物头部写了 `> 依据 facts vN 生成`，并与 facts、state 一致；阶段 0 使用 v0
- [ ] `state.yaml` 的 `stage`、`artifacts`、`open_bugs`、`pending_decisions` 及本阶段机器字段已更新
- [ ] 没有把"待确认"悄悄当成"已确认"往下传；进入阶段 8 前 `pending_decisions` 必须为空
- [ ] 本阶段没有替用户做业务判断
- [ ] 没有跨角色越界（前端不改后端、测试不改代码、开发不改契约）
