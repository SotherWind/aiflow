# 阶段门禁检查表

每阶段收尾前逐条自检。**任一条不通过，不许进入下一阶段。**

带「用户确认」的阶段，按 `references/review.md` 走；追问按 `references/grilling.md` 走。

## 阶段 0 · 需求澄清（需求分析师）→ `00-intake.md`

- [ ] 能用**一个名词**说清本轮的业务对象
- [ ] 大词已拆成 4–8 个纵切，且**只选第一个**
- [ ] 有一句明确的：`本轮做：X ｜ 本轮不做：Y、Z、W`
- [ ] 有形态判断（流程型 / 计算型 / 批处理型 / 并发型 / 效果型）
- [ ] 有一句明确的：`风险线索：<并发写入 / 数值精度 / 批处理 / 无>`
- [ ] 风险线索只标不问结论，**没有在阶段 0 拍板技术方案**
- [ ] 影响范围的问题按决策树逐轮问完，`questions.md` 里没有「待问 / 待答复」；没有问题时写「无」，不得硬凑
- [ ] **用户确认了范围**：`00-intake.md` 有用户确认，`signoffs.scope: confirmed`

## 阶段 1 · 需求调研（需求分析师）→ `01-research.md`

- [ ] 写清现状：现在这件事怎么做的（人工 / 旧系统 / 没有）
- [ ] 写清约束：期限、已有系统、必须对接的东西
- [ ] 参考了至少一份同类做法，并写了"我们不照抄哪一点"
- [ ] 没搞清的问题逐条追问到底，没有留给 PRD
- [ ] facts 的每条 R 来源都是「已确认」，没有「假设 / 待确认」
- [ ] **用户确认了需求**：`01-research.md` 有用户确认，`signoffs.requirement: confirmed`

## 阶段 2 · PRD 与产品原型（产品经理）→ `02-prd.md`、`02-prototype.md`

- [ ] 每条验收标准都能写出至少一个失败用例，都引用了 R 编号
- [ ] 状态机完整，含"到点自动发生"的动作
- [ ] 非功能要求是具体数字；明确写了**不做什么**
- [ ] 交付形态判断写了理由，与 `prototype_required`、`design_required` 一致
- [ ] **用户确认了 PRD**：评审记录没有「待修改 / 待澄清」，`signoffs.prd: confirmed`
- [ ] 需要原型或设计稿时：`.aiflow/design-system.md` 写明了设计规范的来源（已有规范，或经用户确认的「无，按默认」），交付形态判断里有「设计规范」一行
- [ ] 需要原型时：达到 `references/prototype.md` 的中保真要求（真实组件、真实文案、功能色）；有全局说明、页面流程图、角色 × 状态矩阵；每页带编号标注；每页都对应至少一条 A，有空 / 加载 / 出错 / 无权限状态；文件不依赖外部样式、用用户的查看方式打开过；**用户确认了原型**，`signoffs.prototype: confirmed`
- [ ] 需要原型时：每个页面运行 `layout-check.js`（样式包自带），没有报出文字或图标偏移、换行、溢出
- [ ] 不需要原型时：`signoffs.prototype: skipped`
- [ ] 跑过断点自查 B1、B7

## 阶段 3 · 设计稿（体验设计师）→ `03-design.md`

不需要设计稿时跳过：`signoffs.design: skipped`，没有 `03-design.md`。

- [ ] 设计稿覆盖原型的全部页面（没有原型时覆盖 PRD 主流程的全部页面），每页画了空 / 加载 / 出错状态
- [ ] 设计规范有具体取值（颜色、字号、间距、圆角）；沿用已有规范时，取值和 `.aiflow/design-system.md` 一致，没有另起一套
- [ ] 每条交互标注 `I` 写了触发、响应和反馈文案
- [ ] 走查点 `W` 每条能判真假；每页至少一条，每条交互标注至少被一条覆盖；关键项已标出
- [ ] 设计稿文件能打开
- [ ] 每个设计稿页面运行 `layout-check.js`，输出为空；每页有一条通用版式走查点
- [ ] **用户确认了设计稿**：评审记录没有「待修改 / 待澄清」，`signoffs.design: confirmed`
- [ ] 跑过断点自查 B7

## 阶段 4 · 技术架构（技术架构师）→ `04-arch.md`、`04-mapping.md`

- [ ] **四问都有答案**：A 成立物理上要求什么 / 在哪一层保证 / 有无并发写 / 失败怎么表现
- [ ] 每条验收标准落到「由哪条约束保证」，而不是「写在某个函数里」
- [ ] 能放数据层的约束没有放在应用层（唯一索引、非空、条件更新）
- [ ] **技术栈可行性校验过**：每条关键约束需要的机制，在选定选型里真实存在；给不了的已换选型或记为技术债
- [ ] 有并行分支的流程，用了依赖图 + 推进条件，没有硬压成单线状态机
- [ ] 架构产物只包含推导得出的内容，没有为凑整齐补的空章节
- [ ] 五样信息可定位：数据怎么存 / 每条 A 由哪条约束保证 / 有无并发写 / 失败怎么表现 / 做什么与不做什么
- [ ] 有原型或设计稿时：页面要展示的字段、交互标注里的失败反馈，在契约里都有着落
- [ ] **由测试角色试读一遍**：按上面的五样去方案里找，任意一样找不到，退回重写
- [ ] 映射表没有「无对应」，且没有虚构尚未产生的 T/E 编号
- [ ] 数据模型能支撑全部状态流转，不需要二次改表
- [ ] 「到点自动发生」的规则配了定时任务 + 幂等
- [ ] 错误码统一成表
- [ ] **并发问题做了判断并留痕**：结论为「存在」→ 每个共享状态都有策略与落点；结论为「不存在」→ 写了理由
- [ ] 若判定存在并发写：每处「先查后改」都回答了"两次查之间被改了怎么办"，并有数据库约束、原子更新、锁或串行化兜底
- [ ] 跑过断点自查 B2、B3

## 阶段 5 · 任务拆分（技术架构师）→ `05-tasks.md`

- [ ] 每个任务有编号 `T1..Tn`、类型 `FE`/`BE`/`JOB`、验收标准、依赖、测试要点
- [ ] 批处理与定时任务标成了 `JOB`，没有混进 `BE`
- [ ] 每个任务都是"一人能独立开发、另一人能独立验收"的颗粒
- [ ] 前几个任务能串成一条可跑通的主流程；风险任务排在前列；标了可并行的任务
- [ ] 有原型或设计稿时：每个页面 `P` 都落到了至少一个 FE 任务
- [ ] 已在 `04-mapping.md` 回填真实 T 编号；E 留到阶段 8 回填

## 阶段 6 · 开发（前端 / 后端）→ 代码 + `06-dev-log.md`

- [ ] 每个任务在日志里有：编号、类型、状态、涉及文件、测试要点
- [ ] `state.yaml.task_status` 覆盖全部 T，且进入阶段 7 前全部为 `done`；部分完成或未开始不得带过去
- [ ] 前端字段名与后端契约完全一致
- [ ] 有设计稿时：设计规范照抄取值，交互标注逐条实现
- [ ] 服务端校验齐全（不只依赖前端）
- [ ] 状态变更落库且可追溯；定时任务有幂等
- [ ] 测试断言能读出对应验收标准，失败路径 ≥ 30%
- [ ] 跑过断点自查 B4

## 阶段 7 · 设计走查（体验设计师 ⇄ 前端）→ `07-walkthrough.md`

不需要设计稿时跳过：`walkthrough_result: skipped`，没有 `07-walkthrough.md`。

- [ ] 在浏览器里打开实现页面走查，没有凭读代码推断；走查对象、走查人、视口写在头部
- [ ] 每个实现页面运行了 `layout-check.js`，输出原文作为通用版式点的证据
- [ ] 每个走查点都有结果和证据；只用 `03-design.md` 里定义过的 W 编号，走查时没有改分母
- [ ] **还原度 ≥ 90%**（每个走查点取最近一轮结果），并且**关键项全部通过**
- [ ] 不通过的点都开了 `UX-n` 问题单并派给前端；前端改完由体验设计师复查，前端没有自己关单
- [ ] 问题单没有「待修复 / 待复查 / 打回」；非关键项的遗留写进了结论
- [ ] `walkthrough_result: pass`，`open_ux_issues` 为空

## 阶段 8 · 测试（测试工程师）→ `08-test-report.md`

- [ ] **每个任务**都有独立结论；未开始不是可接受的测试结论
- [ ] 每个任务的失败路径用例 ≥ 三分之一
- [ ] 用例有 E 编号并带验收标准编号；已在映射表回填 E
- [ ] 每条当前有效 A 至少一条已执行用例，`acceptance_results` 有 `pass/fail` 结果；`uncovered` 阻塞
- [ ] 不通过的任务都开了缺陷单，**且已派给对应开发**（FE→前端，BE/JOB→后端）
- [ ] `JOB` 任务额外测了三类：部分失败、断点续跑、重复执行幂等
- [ ] 架构文档判定「存在并发写」时，每个共享状态都有并发正确性用例（同时发起，断言最终值与成功次数，不是压测）
- [ ] 未覆盖项已补测，或通过 facts 变更移出本轮；不得只写原因放行
- [ ] 跑过断点自查 B5

## 阶段 9 · 缺陷修复与复测（开发 ⇄ 测试）→ `09-bugs.md`

- [ ] 每条缺陷有：关联任务、归属（FE/BE）、现象、复现、根因、影响面
- [ ] 修复是最小改动，一次只修一个
- [ ] 每条都有「修复说明 + 待验点」
- [ ] 每条都有测试的**复测结论**（没有口头通过）；打回的单都写了原因（现象/环境/复现）
- [ ] 有设计稿时：FE 缺陷修复改到已走查的页面，体验设计师复查了受影响的走查点
- [ ] 跑过断点自查 B6

**清零门禁（进入阶段 10 的硬条件）**

- [ ] `state.yaml` 的 `open_bugs` 为空
- [ ] `09-bugs.md` 没有「待修复」「待复测」「打回」状态
- [ ] 每条已关闭缺陷都有复测结论

> 三条全满足才能进阶段 10。**不许带 bug 进回归。**

## 阶段 10 · 全量回归（测试工程师）→ `10-regression.md`

- [ ] 回归范围从已关闭缺陷的「受影响任务」推导而来，有过程
- [ ] 主流程全跑一遍，不管有没有被影响
- [ ] **所有当前有效 A 都有执行结果**；主流程和影响面不能替代全量验收覆盖
- [ ] `acceptance_results` 中所有当前有效 A 均为 `pass`，无 `uncovered`
- [ ] `pending_decisions` 为空
- [ ] 有设计稿且关闭过 FE 缺陷时，「设计还原复核」结论为通过
- [ ] 结论明确：通过 / 有条件通过（列条件）/ 不通过（列阻塞项），并与 state 一致

**上线门禁（进入阶段 11 的硬条件，只有两种可放行路径）**

- [ ] 「通过」；或「有条件通过」且条件非空、用户已显式确认并记录
- [ ] 「不通过」一律退回；任何缺失或无法解析的结论也退回

- [ ] 回滚方案是可执行步骤，不是"回滚到上一版"，并在测试环境走过一次
- [ ] 上线检查表逐项可勾选
- [ ] 数据变更说明了是否可逆、备份在哪
- [ ] `11-release.md` 已填写实际执行结果、证据和观察窗结论
- [ ] `release_status: verified`；`planned/deployed` 尚未完成，`rolled_back` 不算上线成功
