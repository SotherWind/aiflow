# 评审确认协议

适用：范围（阶段 0）、需求（阶段 1）、PRD 与原型（阶段 2）、设计图片及最终 HTML 设计稿（阶段 3）、技术栈（阶段 4），以及回归有条件放行（阶段 10）。

规则只有一句：**用户明确确认之前，这个阶段没有完成。** 用户提了问题就照着改；有不清楚的地方，按 `references/clarification.md` 追问；改完再请他看，直到他确认为止。

## 前置：共识与产物分开确认

先按追问协议查证、分轮提问，直到本轮前沿为空；在对话里展示结论、取舍与默认清单并取得共识确认，或有充分已知输入而记录 `not_needed`，然后才生成正式产物。**“先交文件、等用户挑错”不是澄清流程。**

共识确认记录在 `state.clarification` 和过程记录中；产物评审确认记录在产物与 `signoffs` / 技术栈锁定字段中。只有同一份已经完整展示并明确同意的结论，才可引用同一消息，免于机械重复；确认理解一致不能自动认可尚未展示的 PRD、原型、设计稿或选型细节。

评审新引出实质分叉时，先记反馈，重开 `clarification: pending`，问清并确认本轮共识后再修改受影响产物；原文件与历史确认保留可追溯，按变更协议处理，不把旧确认复制给新内容。

## 一、一轮评审怎么走

阶段 3 先评审生图工具实际生成的图片：主会话直接展示，用户反馈后编辑图片再展示，循环到明确认可当前版本。此时用 `design-images.md` 记录，不要求 `03-design.md` 或 HTML。图片确认后才制作 HTML；最终评审再查看真实文案、组件、状态、响应式与还原结果。调用工具成功、用户没回复或关闭弹层，都不是确认。细节见 `experts/ux.md`。

1. **交付**：告诉用户看什么、在哪看（文件路径；原型和设计稿给能直接打开的路径或地址），附一份不超过 10 行的摘要和「按默认处理」清单。
2. **请他确认**：按 `references/clarification.md` 的提问通道选择可用于确认的交互式工具，提供「确认，没问题」和「有问题，我来提」；工具不可用或不允许用于确认时，直接用文字请求明确答复。
3. **记录反馈**：用户的每条意见原样记进产物的「评审记录」，一条一行，编号 `F1、F2……`。
4. **逐条处理**：
   - 意思明确：照改，在「处理」列写改了什么
   - 意思不明确：按追问协议在对话中问清楚，再改产物并追加问题归档
   - 改了会冲突（和已确认的规则或别的反馈矛盾）：把冲突摆给用户选，不自己取舍
5. **再交付**：列出「这一轮改了什么」，逐条对应 F 编号，然后回到第 2 步。

循环到用户明确确认为止，不设轮次上限。

## 二、什么算确认

| 算 | 不算 |
|---|---|
| 「确认」「没问题，往下走」「可以」 | 「嗯」「先这样吧」「差不多」：追问一次，是确认通过，还是还有要改的 |
| 在结构化提问里选了「确认，没问题」 | 用户没有回复 |
| | AI 自己判断「应该没问题了」 |

确认后，在产物的「用户确认」小节写三行：

```
- 确认结论：已确认
- 用户原话：「确认，往下走」
- 确认时间：2026-11-01T10:20:00+08:00
```

范围、需求、PRD、原型和最终 HTML 设计稿分别更新 `state.yaml.signoffs` 的对应项。图片确认只更新 `design_image_status` 与图片指纹，不提前确认 `signoffs.design`。技术栈按 `references/tech-stack.md` 确认具体方案、生成指纹，再写 `tech_stack_status: locked` 与 `tech_stack_fingerprint`。

回归有条件放行也不新增 signoffs 键：条件逐项记录在 `10-regression.md` 并与 `regression_conditions` 一致，在同一文档记录确认后再设 `regression_user_confirmed: true`。条件改变后标记改回 false，重新确认。

> **用户原话只能来自用户本人的消息。** AI 不得代填。子代理接触不到用户，所以评审确认只能在主会话里做。

## 三、评审记录格式

```
## 评审记录

| 轮次 | 编号 | 用户反馈（原话） | 处理 | 状态 |
|---|---|---|---|---|
| 1 | F1 | 「列表里要能看到超时多久了」 | 列表页加「已超时 X 分钟」列，见 P2 | 已处理 |
| 1 | F2 | 「驳回之后客户还能改描述吗」 | 追问中，见 Q12 | 待澄清 |
```

状态只有四种：`待修改`、`待澄清`、`已处理`、`不改`。`不改` 必须写理由并经用户同意。确认之前，表里不能有「待修改」或「待澄清」。

## 四、确认之后又要改

确认过的产物冻结。之后业务需求要改（用户新提，或下游发现问题），走 `references/change.md`：先改事实源和产物，把对应的 `signoffs` 改回 `pending`，**重新走一遍评审确认**。技术栈更换或超出锁定版本范围时，按 `references/tech-stack.md` 解除锁定并重新确认，不为纯技术变更提升 facts 版本。下游已经开工的，按影响面复核。

仅原型或设计细节变化、不改业务判定时不提升 facts 版本，但受影响确认仍要重做。失效产物先按变更协议留快照、登记失效清单；本轮草稿不复制旧确认当作新同意。清除失效待办与恢复 `confirmed` 的依据是实际复核和必要用户确认，不是文件重新存在。

## 五、各节点确认什么

| 节点 | 产物 | state 字段 | 用户确认的是 |
|---|---|---|---|
| 阶段 0 | `00-intake.md` | `signoffs.scope` | 本轮做什么、不做什么 |
| 阶段 1 | `01-research.md` | `signoffs.requirement` | 业务规则全部问清，没有遗留问题 |
| 阶段 2 | `02-prd.md` | `signoffs.prd` | PRD 没问题，包括「要不要原型、要不要设计稿」的判断 |
| 阶段 2 | `02-prototype.md` + 原型文件 | `signoffs.prototype` | 原型没问题；不需要原型时为 `skipped` |
| 阶段 3 · 图片 | `design-images.md` + 生图原图 | `design_image_status` + `design_image_fingerprint` | 已展示的图片版本与视觉方案认可，可以开始制作 HTML |
| 阶段 3 · HTML | `03-design.md` + HTML + 浏览器截图 | `signoffs.design` | 按确认图片还原后的完整设计稿；不需要设计稿时为 `skipped` |
| 阶段 4 | `.aiflow/tech-stack.md` | `tech_stack_status` + `tech_stack_fingerprint` | 最终技术组合、版本范围、理由与取舍 |
