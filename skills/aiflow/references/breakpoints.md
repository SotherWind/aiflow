# 六条断点自查

在阶段 2、5、7 结束后各跑一遍。每条只问一个问题：**这里有没有出过问题？**

对应关系：阶段 2 查 B1；阶段 5 查 B4；阶段 7 查 B6。B2、B3 在阶段 3 收尾时查，B5 在阶段 6 收尾时查。

## B1 · 需求调研 → PRD

**问：** PRD 里有没有哪句验收标准，是我自己"补圆"出来的，而不是用户或材料里明确的？

**命中信号：** 写的时候觉得"这里应该是这样"，但找不到出处；或者原文模糊，我直接选了一个解释。

**处理：** 退回阶段 1，把这条标成「待确认」，去问用户。不要带着假设往下走。

## B2 · PRD → 技术方案

**问：** 每条验收标准都能在契约里找到对应的字段、校验或任务吗？

**命中信号：** 映射表里出现"无对应"；或者某个字段找不到它服务的是哪条验收。

**处理：** 对照 `03-mapping.md` 逐条走。缺的一侧要么补契约，要么退回去改验收标准。

## B3 · 技术方案 → 代码

**问：** 代码里的字段名、错误码、分层，是不是都能对回契约？

**命中信号：** 实现里冒出了契约里没有的字段；错误码在代码里现编；同一概念两个命名。

**处理：** 以契约为准改代码。如果确实是契约漏了，先走 `references/change.md`：更新 facts 05 节、按需升语义版本、重算影响面并更新架构与映射，再改代码。不得只在下游直接补契约。

## B4 · 代码 → 单元测试

**问：** 随便挑三条断言，能不能说出它在验证哪条验收标准？

**命中信号：** 断言只有 `status === 200`、`res.body` 存在这类；测试名是"should work"；失败路径用例占比低于 30%。

**处理：** 重写这部分测试。要求每条断言带验收标准编号。

## B5 · 代码 → 冒烟与端到端

**问：** 这些用例如果换一套完全不同的实现，还能通过吗？

**命中信号：** 用例里出现了 CSS 选择器路径、内部函数名、具体实现细节；改个类名就全红。

**处理：** 改成从用户动作出发描述用例；用例的锚点应该是业务语义，不是实现细节。

## B6 · 缺陷修复 → 回归

**问：** 这个补丁改完之后，有没有人能说清"哪些地方可能会被带坏"？

**命中信号：** 回归范围写的是"全测"或者"挑几条常用的"；补丁改动了公共方法但没列出调用方。

**处理：** 先输出影响面清单，再定回归范围。

## 断点日志模板

追加到 `.aiflow/breakpoint-log.md`，每条七行，不要写成长段落。

```markdown
## 2026-11-03 · B2

- **阶段**：2 → 3
- **我给的输入**：PRD 第 3.2 节验收标准 A3
- **AI 的输出**：查询接口加了 isOverdue 字段
- **问题**：把"自动标记"理解成"查询时计算"
- **我改了什么**：事实源补一条约束——状态变更必须落库，校验必须在服务端
- **如果重来**：先写状态机，再让它生成契约
- **耗时**：AI 3 分钟，我改 25 分钟
```

最后两行是这份日志最值钱的部分。攒够两周，你会看到出错位置高度集中在几个固定接缝上——那时候这份日志本身就是一份可以拿去分享的材料。
