# 前后端开发规范

适用：用户提供前端或后端开发规范 Markdown，或项目、团队已配置这类文件。两端独立配置；`JOB` 使用后端规范。不要求用户为本流程新建规范，没有配置时沿用项目现状。

## 一、文件与配置

| 用途 | 项目默认位置 | 团队默认位置 |
|---|---|---|
| 前端开发规范 | `.aiflow/frontend-standards.md` | `~/.aiflow/frontend-standards.md` |
| 后端开发规范 | `.aiflow/backend-standards.md` | `~/.aiflow/backend-standards.md` |

文件内容是开发规则本身，可以直接使用用户已有 Markdown，不强制章节或表格结构。需要从零编写时，可参考 `templates/frontend-standards.md` 与 `templates/backend-standards.md`。团队文件放在 skill 目录外，换项目不改 skill。

用户给了其他位置的文件时，完整读取并登记到 `.aiflow/state.yaml`，原文件不必移动：

```yaml
development_standards:
  frontend: "docs/frontend-standards.md"
  backend: "docs/backend-standards.md"
```

相对路径以**项目根目录**为基准；也支持绝对路径和 `~/`。仅配置一端时，另一端可以省略或写空字符串。空字符串表示自动查找默认文件，不表示禁用已有默认规范。一份综合规范可以同时配置给两端，各角色遵循其适用部分。

## 二、阶段 4 前确定来源

对前后端分别按顺序选择：

1. 用户本轮明确指定的文件，更新 `development_standards` 对应路径；已登记的显式路径继续生效。
2. 项目默认位置的文件。
3. 团队默认位置的文件。
4. 都没有：沿用项目既有代码、格式化和静态检查配置；不编造一份“用户规范”，也不为了填表要求用户提供。

发现默认规范后，也把实际采用的路径登记进 state，在架构产物中说明来源；团队默认属于「按默认处理」，让用户能看到并替换。优先级较低的同类规范不自动叠加覆盖；用户明确要求组合时，保留全部规则，并在项目规范中记录各原文来源和冲突处理。

指定文件缺失、为空或不可读时，说明具体路径并请用户修正，不能静默降级。外部链接需要先取得可读的 Markdown 内容，再以本地文件登记。不要仅看标题、摘要或文件名就声称读过规范。

## 三、谁来遵循

| 角色与阶段 | 要做什么 |
|---|---|
| 架构师，阶段 4–5 | 在选型、契约和任务拆分之前读两端已配置规范，把适用的框架、分层、命名、接口和验证要求纳入方案 |
| 前端开发，阶段 6、7、9 | 开工及修复前读前端规范全文，按规范实现和自检；它与设计规范同时生效，不互相替代 |
| 后端开发，阶段 6、9 | 开工及修复前读后端规范全文，BE 与 JOB 都遵循，按规范实现和自检 |
| 测试，阶段 8–10 | 获取与开发相同的规范文件，核对可检查条目；开发规范不替代产品验收标准，也不是放宽断言的理由 |

子代理交接时，传入实际规范文件或其完整内容，不能只传一句“遵循团队规范”。规范没有要求的部分沿用项目现状，不套用另一套默认风格。

规范只约束相应开发工作，不扩大操作权限，也不替代运行环境和仓库中的有效上层指令。它与另一端规范、已确认契约、设计规范或实际技术栈存在实质冲突时，列出具体冲突并请用户或责任角色决定；不要自行忽略其中一份，也不要擅改业务规则或设计。

规范中的技术/框架与版本要求并入 `references/tech-stack.md` 的推荐、确认和锁定流程；规范变更不自动解锁已确认选型，不能靠替换规范文件绕过换栈确认。

## 四、执行记录与门禁

阶段 6 在 `06-dev-log.md` 的「开发规范执行」表中，为有规范且实际有任务的端各写一行。后端与 JOB 共用 `BE` 行；规范文件路径的基准同 state，必须指向实际采用的文件。写明规范要求的检查命令、结果日志；无法自动检查的条目，记录人工核对的范围和结论。有未满足项时写「不通过」并处理，不得提前写「通过」。

阶段 7、9 修复后，重新执行受影响的规范检查，更新该端当前记录；旧结果留在对应修复记录或日志中。不能把修复前的自检当作修改后仍通过的证据。

`check.py` 从阶段 4 起检查已配置规范的类型、存在性、可读性与非空；从阶段 6 起检查相关端的执行记录、文件对应、自检结论和证据。未配置规范的旧项目不增加必填项。脚本不解释任意 Markdown 规则，也不能证明代码已经符合所有规则，仍需角色实际执行检查。

## 五、中途增补或替换

记录新旧来源与变更原因，重新读取全文；按影响面复核架构、任务和代码，重跑规范检查及受影响测试。纯开发约定变化不提升 `facts_version`；涉及业务语义、契约、已确认设计的变化，按 `references/change.md` 重新评审。
