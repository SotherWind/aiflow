# 追问协议

适用：全部角色遇到需要用户决定的事项时。主会话负责访谈；子智能体按 `references/orchestration.md` 返回证据、问题与推荐，主会话结合全局上下文查漏、提问并接收答复。

持续追问，直到双方对要做的事情理解一致。把需求当作一棵**决策树**：每个答案都会展开依赖它的下一层决定。先理解用户想达成什么，再深入场景、规则、取舍和异常；阶段 0 可用 `references/discovery.md` 帮助展开思路。

## 按轮推进

**前沿**是前提已经明确、现在就能问的全部问题。一轮问完整个前沿，逐题编号，给出推荐答案及其理由，然后等待用户回答。题数由实际问题决定。依赖本轮另一个未答问题的，留到其答案明确后再问；主题不同本身不构成依赖。

每次答复都会重塑决策树：沿答案继续追问，检查它带来的新选择、矛盾和遗漏。部分答复只解决对应问题。用户说「全部按推荐」表示接受本轮已展示的建议，仍要展开由此产生的新分支。

事实自己查，决策交给用户。先读已有资料，能从代码、配置或公开资料查到的自己查；需要外部案例支撑选择时按 `references/research.md` 调研。查证未完成只暂停依赖它的问题，其他独立问题照常问。已经明确的事实和要求直接采用。

提问用产品场景解释差异，让用户能作出选择。推荐应服务于用户目标，说明依据和代价；关键前提未知时给条件建议。互斥方案用单选，能组合的能力允许多选，也接受开放回答。

## 提问通道：弹层优先，文字兜底

优先调用当前环境实际提供的交互式提问工具，让用户在宿主的弹层或选项卡中作答，例如 `request_user_input_async`、`request_user_input` 或 `AskUserQuestion`。遵守工具的可用模式、用途和参数；工具可用且适合表达题目时，直接调用，不只在正文列选项。

题目中保留编号、必要背景与推荐理由；推荐选项明确标注，并允许用户补充自己的答案。同一轮问题超过工具容量时分批展示，保持题号与未答问题，继续问完当前前沿；分批不意味着这轮已经收口。

工具不存在、当前模式不允许、调用失败，或无法完整表达某道题时，该题退回编号文字。多选题用工具的多选能力；没有这项能力就用文字接受 `A+C` 等组合，不改成单选，也不删减选项。其他适合工具的问题仍用交互式提问。

提交问题后等待真实答复；异步工具返回不代表用户已回答。跳过、关闭或没有返回答案都不算接受推荐，未答项继续保留，必要时用文字补问。

文字兜底格式：

```text
❓ Q1 · <问题标题>：<问题、可选方向；可组合时说明可多选>

➡️ 推荐：<答案及理由，必要时说明适用前提与取舍>

---

❓ Q2 · ...
```

## 何时收口

当前范围的各条决策分支都已探索，待答问题、矛盾和影响范围的静默假设都已消除，才算前沿为空。用完整用户路径反查遗漏，不能把「刚才那批题答完了」当成「需求问清了」。更晚阶段才需要的细节可以后续细化，但本阶段依赖的前提现在就要明确。

前沿为空后，在对话中汇总目标、本轮范围、关键决定、默认项和排除项，请用户确认理解一致。同一份完整结论已有明确确认时引用原消息；输入已经充分明确时直接采用，毋须硬凑访谈。遇到新分歧就继续问。

## 先对话，后文件

访谈中的问题、答案、推荐和查证依据留在对话里。新项目此时不创建 `.aiflow/`，包括 `questions.md`、状态文件和占位文档；问清并确认共识后才统一落档。用户明确要求中途保存时，可以保存真实进度，标明未完成，继续追问。

已有项目保留原文件；进入新的澄清时仅将已有 `state.clarification` 标为当前阶段 `pending`，防止继续执行。新问题仍先在对话里问清，收口后再追加台账、更新受影响产物。实际测试、缺陷和运行证据照常如实记录。

**只有收口后需要写文件，或用户要求中途保存时，才读 `references/clarification-records.md`。** 归档格式不决定访谈内容。产物生成后需要评审时按 `references/review.md` 处理。
