# 技术栈推荐、确认与锁定

适用：阶段 0–1 收集用户技术要求，阶段 4 确定选型，以及开发、修复或变更涉及技术栈时。选型独立记录在 `.aiflow/tech-stack.md`，不限制 `04-arch.md` 的正文结构。

## 一、先收集约束

需求分析师记录用户明确指定的语言、框架、数据库、运行时和版本要求，区分「必须」与「偏好」，保留来源。不把用户指定的要求写成 AI 的默认决定；阶段 0 只记录，不替用户改选型。

架构师先读项目依赖清单、锁文件、构建与部署配置、设计规范、已配置前后端开发规范，再整理：

- 用户硬性指定：作为边界；做不到就说明冲突，不能悄悄替换。
- 用户偏好：优先考虑，偏离时说明原因并请用户选择。
- 已有项目：优先建议沿用兼容的现有技术栈，说明实际版本来源；不因个人偏好换框架。
- 开发与设计规范：提取其中的框架、组件库、分层和版本约束；有实质冲突先解决，不自行判定某一份无效。

先在对话中保留这些事实与来源，按 `references/clarification.md` 把影响选型的未知决策分轮问清，收口后才整理台账与选型文件。它们不是业务规则 R/A；和业务语义发生关联时，仍按事实源变更规则处理。

## 二、未指定部分主动推荐

根据已确定的前提，在当前前沿的问题中推荐可行选择，并说明差异与取舍；依赖未回答问题的选型留到后续轮次。没有合理备选时说明原因，不为凑选项造方案。用户已经给出的硬性指定不重复询问，但冲突和做不到的要求必须先解决。

澄清收口后再整理完整组合，写明用途、技术/框架标识、可判定的版本范围、来源和选择理由；这些信息写进正式选型文件。整包最终评审不能代替前面的逐轮澄清。

「选型清单」只列本轮实际采用且需要锁定的项，编号 `S1..Sn`；不适用的前端、数据库等维度在说明中写理由，不为填表引入依赖。不需要锁定每个间接依赖。

来源只写「用户指定 / 沿用项目 / 开发规范 / 推荐」。推荐项的「备选与取舍」必须填写。版本不能写 `latest`、`*`、待定或按默认；核对官方文档和项目配置后给明确版本或范围，并验证运行时、框架与数据库的兼容性。用户指定的版本不能因不是最新就被擅自升级。

## 三、确认后锁定

1. 前置澄清收口、`state.clarification` 已完成后，才按 `templates/tech-stack.md` 写完整方案，`state.tech_stack_status` 仍保持 `pending`（它是选型审批状态，不是澄清状态）。
2. 在主会话向用户展示最终组合、版本范围、选择理由、必要备选、冲突处理和未指定项的推荐，请用户明确确认。仅同意流程、泛泛说「你定」、或者没有回复，都不能当成对尚未展示的选型的确认。
3. 用户确认具体方案后，按 `references/review.md` 在该文件最后的「用户确认」记录原话和时间。评审意见全部处理完；指定或沿用的选型也要确认最终组合，已有明确同意完整组合的消息可作为依据，不必机械重复询问。
4. 运行只读指纹命令：

   ```text
   python "<本 skill 目录>/scripts/check.py" "<项目目录>" --tech-stack-fingerprint
   ```

5. 将输出写入 `state.tech_stack_fingerprint`，再设 `tech_stack_status: locked`，运行完整 `check.py` 门禁。退出码 0 才能完成阶段 4。

指纹命令只生成 SHA-256，不确认选型、不更新 state，也不代表阶段通过。指纹绑定「用户确认」之前的完整方案；确认小节必须是最后一个二级小节，指纹本身只放在 state 和开发核对记录中，不写回方案正文。

## 四、开发与验收

前后端开发、测试和发布角色都获得完整选型文件与 state。开发及修复使用已锁定组合，不得用开发规范、个人偏好或临时困难自行替换。当前实现无法满足要求时，先提出冲突与替代建议，等用户批准。

阶段 6 的 `06-dev-log.md` 增加「技术栈核对」：记录当前指纹，每个 S 各一行，填写实际技术/框架、实际版本、核对结论与证据。技术标识与选型清单一致；证据给出真实依赖/锁文件位置、构建或实际运行版本输出，不是把预期版本抄成实际版本。版本范围的满足情况用对应生态工具核对；无法验证时阻塞，不写「通过」。

阶段 7、9 修复影响依赖、构建或运行时后，重新核对受影响项，更新当前记录。测试独立读取实际项目与配置，不用开发自报通过代替验证；发布前也核对目标环境和构建产物。

`check.py` 检查选型完整性、用户确认、锁定指纹、逐项执行记录、技术名称与精确三段版本的一致性。其他版本范围与兼容性由对应生态工具核对并留证，脚本不是通用版本范围解析器，也不能证明证据或用户原话真实。

## 五、更换或升级

保存旧方案与确认记录；将状态改回 `pending`、清空锁定指纹，记录变更原因和影响面。有未确定的取舍时先重新澄清并确认共识，再更新正式方案、重新评审和锁定。不得只改名称、版本或指纹而复用旧确认。

已有架构、任务、代码、测试和发布内容按影响面复核，开发核对记录必须绑定新指纹。只改技术栈不提升 `facts_version`；改变业务语义、契约或已确认设计时，按 `references/change.md` 处理。锁定范围内的版本更新不重新确认选型，但仍需核对实际版本并跑相关测试。

旧项目若已到阶段 4 或之后，补录真实现状和技术要求，请用户确认后锁定；不能由 AI 补造历史确认。
