# 需求变更怎么处理

真实项目一定会变。这套流程如果只能一次跑到底，那它就是个演示品。

## 业务需求的入口：事实源

本协议处理业务需求变更，从 `.aiflow/facts.md` 进来。仅增补或替换开发规范、不改业务语义时，按 `references/development-standards.md` 做影响复核和重验，不为纯开发约定提升 facts 版本。仅更换技术栈或超出锁定版本范围时，按 `references/tech-stack.md` 将选型改回 `pending`、清空指纹，展示新方案并重新确认锁定；不为纯选型变更提升 facts 版本，也不能借修改规范绕过锁定。业务需求变更有两个触发源：

1. 用户明确提出（「加一个状态」「这个字段不要了」）
2. 阶段中发现事实源本身写错了（调研漏问、规则理解偏）

**不许在下游产物里直接改。** 改 PRD 不改 facts、改代码不改契约，都是断链的起点——下一个人重跑时会把它改回去，而且没人知道当初为什么改。

## 四步

### 1. 先澄清变更，再改事实源

- 变更含义或取舍不明确时，先按 `references/clarification.md` 在对话中逐轮问清、确认共识，期间保持现有有效事实源和产物不变；收口后再归档并执行以下修改。含义明确时记录依据，不硬问。回退到阶段 0–4 后补本阶段澄清记录，不能沿用别的阶段收口状态。
- 修改前把当前 facts、state、相关产物及原型/设计文件复制到 `.aiflow/history/<本次变更编号>/`，保留原始确认与执行证据；不要覆盖已有快照。产物检查只读取 `artifacts/` 的当前文件，不把 history 当作当前输入。
- **语义变更**：追加新编号（R11、A15），旧条目划掉不删，`facts_version` +1
- **文字修订**：不改变判定含义时只同步文字，不升版本
- 在 06 变更记录写清：改了什么、为什么、影响哪些编号

### 2. 算影响面

| 改了什么 | 必须重写的产物 | 必须复核的下游 |
|---|---|---|
| 新增 A15 | 02–06、08、10、11 中 A15 相关部分 | 阶段 2–11 全部当前产物 |
| 修改 A3 的判定条件 | 作废旧 A、新增 A；重写上述相关部分 | 阶段 2–11 全部当前产物 |
| 删除 A7 | 移除 02–06、08、10、11 的当前有效引用；09 旧单归档，未关闭问题迁移或明确处置 | 检查其他 A 与发布内容是否依赖 A7 |
| 只改措辞、不改判定 | 同步文字，不升版本 | 无 |
| 改了 R 但没改 A | 先确认 A 是否应变化，再更新 02–06、08、10、11 | 阶段 2–11 全部当前产物 |

回退到最早需要重做或重新确认的阶段：范围变了回阶段 0，规则变了回阶段 1，验收标准变了回阶段 2，仅设计细节变了回阶段 3。纯设计变更不提升 facts 版本。不要只改 `stage` 后沿用旧结论。

把已经生成、尚未完成影响复核的本阶段及下游产物写入 `state.invalidated_artifacts`，例如：

```yaml
invalidated_artifacts:
  - 03-design.md
  - 04-arch.md
  - 04-mapping.md
  - 05-tasks.md
  - 06-dev-log.md
  - 07-walkthrough.md
  - 08-test-report.md
  - 09-bugs.md
  - 10-regression.md
  - 11-release.md
```

`artifacts` 仍登记目录中实际存在的文件，包括暂留的失效文件；若移入 history，从 `artifacts` 移除，但失效待办保留到重做或处置完成。不为尚未生成的文件创建失效待办。所有角色只使用不在失效清单中的当前产物；即使旧文件的版本号和确认字段完整，失效项也不能继续作为依据。

同时重置受影响的机器状态，历史结果保存在快照中：

| 失效产物 | 当前状态如何重置 |
|---|---|
| 范围、需求、PRD、原型或设计稿 | 对应 `signoffs` 改回 `pending`；新 PRD 明确不需要原型/设计时为 `skipped` |
| 已确认的设计图片或其视觉方案改变 | 保留原图与评审快照；`design_image_status: pending`、清空 `design_image_fingerprint`，重新看图确认后复核 HTML 及下游；不需要设计时为 `skipped` |
| `05-tasks.md` 或 `06-dev-log.md` | `task_status: {}` |
| `07-walkthrough.md` | `walkthrough_result: not_run`；不需要设计时为 `skipped` |
| `08-test-report.md` | `acceptance_results: {}` |
| `10-regression.md` | `regression_result: not_run`、`regression_conditions: []`、`regression_user_confirmed: false` |
| `08-test-report.md` 或 `10-regression.md` | `final_review_result: not_run`、`final_review_evidence: ""` |
| `11-release.md` | 新一轮 `release_status: planned`；这不代表撤销了实际部署，也不授权执行生产回滚 |

未受影响的技术栈锁定、开发规范和角色会话不因回退自动清空。重新进入的阶段按 `references/orchestration.md` 新建协调器和角色，在 `session_log` 用新的执行序号记录，不沿用回退前的会话。回退到阶段 5 前，撤下当前映射中的旧 T/E 回填；阶段 8 前撤下旧 E 回填，分别等任务定义和测试执行后再登记，历史映射保持原样。

仅修正 HTML 对确认图片的还原偏差时，保留图片确认与指纹，更新 HTML 核对证据和受影响的最终确认。替换基准图片时不能只重算指纹沿用旧同意。没有先行生图记录的旧项目保留真实 HTML 历史，再进入阶段 3 做新设计时才启用图片评审。

**未关闭问题不能随失效清单清空。** 保留 `open_bugs`、`open_ux_issues` 和原始单据；回阶段 8 测试、阶段 7 走查前，分别迁移到当前任务、验收或走查点，或取得移出本轮的明确决定并留档。不能把移出本轮伪装成复测通过。仍暂留当前目录的失效问题单会被核对，漏掉未关闭编号也会阻塞。

### 3. 局部重写 + 全量影响复核

`04-mapping.md` 用来定位受影响内容。**局部重写不等于只改一个文件，也不等于全部重新生成。** 每份下游产物都要复核并记录结论；受影响部分重写，未受影响部分明确确认仍可成立。

按阶段推进，当前产物完成复核或更新后，才能把头部升到新 facts 版本，并逐项移出 `invalidated_artifacts`。未到阶段的失效文件可保留，不参与当前校验；当前阶段必需的失效项会直接阻塞。原型或设计不再需要时，先归档旧文件、记录处置结论，再移除失效待办，不能一直挂到发布。

复核结论记录变更编号、影响的 R/A、重做或无影响的理由及验证证据。当前约束映射、契约映射、任务的「验收标准」、测试覆盖和回归执行表只引用当前有效 A；作废 A 可在变更说明与 history 中追溯，不作为本轮实现或验收依据。

只改版本号、清空失效清单或复制旧通过结论而没有复核，视为伪造门禁证据。变更导致的返工记进断点日志。

### 4. 已确认的产物要重新确认

变更碰到了已确认的范围、需求、PRD、原型或设计稿，把 `state.yaml.signoffs` 的对应项改回 `pending`，按 `references/review.md` 请用户重新确认。走查点变了，阶段 7 的还原度按新的走查点重算。

重做产物的「用户确认」先改为待确认，旧原话与时间保留在快照，不自动复制为本轮同意；只有用户确实确认了本轮修改，才同步产物确认和 state。复核确认内容完全不受影响的，记录无影响依据后可保留原确认，不机械重复提问。

变更还影响已锁定的技术栈时，另按 `references/tech-stack.md` 重新确认和锁定，并复核架构、任务、依赖、开发核对记录与测试，不能保留旧指纹继续开发。

## 版本一致性

- `facts.md` 头部写 `> 版本：vN`
- 阶段 1 起的当前有效产物头部写 `> 依据 facts vN 生成`；阶段 0 始终为 v0
- `state.yaml` 的 `facts_version` 与 facts 头部保持一致

`scripts/check.py` 会比对三者。版本缺失、过期或不一致都直接阻塞；必须完成影响复核后才能升产物版本。

检查器只读：检查显式失效状态、旧结果是否清除、当前有效编号与必要确认，不自动回退、归档、判断业务影响或执行验证。不能证明用户原话、无影响结论或执行证据真实，协调者仍要据实处理，不能把移出失效清单本身当作复核。

## 反模式

1. **在下游直接改，不回写 facts。** 最快、最省事、也最容易在下一次重跑时全部丢失。
2. **改一条就不加复核地全量重新生成。** 浪费，且新引入的偏差没人看；正确做法是局部重写、全量影响复核。
3. **把划掉的旧条目删掉。** 失去追溯能力，下次同一条规则又被重新讨论一遍。
4. **用"这次特殊"绕过事实源。** 一旦开了这个口子，事实源就退化成参考资料。
