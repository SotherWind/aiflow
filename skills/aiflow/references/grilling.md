# 追问协议

适用：需求分析师（阶段 0–1）、产品经理（阶段 2）、体验设计师（阶段 3）。架构师、开发、测试遇到业务歧义时，也按本协议把问题交回用户，不自己补。

借鉴 grilling（grill-me）的做法：**把待决事项画成一棵决策树，每一轮问完当前能问的全部问题，直到树上没有未访问的分支。**

## 一、五条规则

1. **事实自己查，决策交给用户。** 能从代码、文档、配置、现有系统查到的，自己去查（可以派子代理查），查不到才问。业务规则、范围取舍、口径选择是决策，必须问。
2. **按决策树分轮。** 每个决策会派生出依赖它的下一层决策。一轮只问「前提都已定下」的那一层，叫前沿。依赖本轮其它问题答案的，放到下一轮。
3. **一轮问完整个前沿。** 不设固定上限，不硬凑，也不为了少问而替用户默认。每个问题编号，给 2–4 个选项，标出推荐并附一句理由，写明它影响哪条 R、A、哪个页面或数据模型。说不出影响什么的问题，不问。
4. **答完重算前沿。** 用户的回答会解锁新的分支，也可能让一些问题作废。重算之后再问下一轮。
5. **问到前沿为空才停。** 每个分支都访问过，没有一条是悄悄假设的。然后把共识整理成小结，按 `references/review.md` 请用户确认。用户确认之前，不得推进阶段。

## 二、问题台账 `.aiflow/questions.md`

所有问题登记在一份台账里，跨阶段共用，只追加不删。格式见 `templates/questions.md`。

| 状态 | 含义 | 算不算解决 |
|---|---|---|
| 待问 | 已识别，但前提未定，还不能问 | 否 |
| 待答复 | 已经问了，等用户回答 | 否 |
| 已解决 | 用户给了明确答案 | 是 |
| 按推荐 | 用户说「你定」「按推荐」 | 是 |
| 移出本轮 | 用户明确同意这一项本轮不做 | 是 |
| 作废 | 前提变了，问题不再成立，写明原因 | 是 |

- 「已解决 / 按推荐 / 移出本轮」必须在「用户答复」列记下用户原话，AI 不得代填。
- 用户的回答引出新问题时，新问题另起编号，在「依赖」列写上原编号。
- 每个阶段收尾时，**本阶段及之前提出的问题必须全部已解决、按推荐、移出本轮或作废**。`check.py` 会查。
- `state.yaml.pending_decisions` 是台账的机器镜像，只列「待问 / 待答复」的编号，两边必须一致。

## 三、一轮提问的格式

有结构化提问工具（`AskUserQuestion`）就用。一次调用装不下时分多次调用，同一轮的问题连续问完。没有结构化工具时，按下面的格式输出，然后停下等回答：

```
第 2 轮 · 2 个问题（Q1、Q2 已答复，解锁了下面两个）

❓ Q3 · 超时从哪个时间点开始算？影响 R6、A10
   A. 从创建时间算（推荐：客户的等待从提交那一刻就开始）
   B. 从分配给坐席的时间算
   C. 其他：____

❓ Q4 · ……
```

用户可以只回「Q3 按推荐，Q4 选 B」。

## 四、三类不许问

1. **能查到的事实**：自己去查。
2. **行业有默认做法的**：按默认做，但必须写进产物的「按默认处理」清单，让用户看得见、能反对。用户看不见的默认，等于替用户做了决定。
3. **纯风格偏好**（命名、目录、注释语言）：跟随项目现状。

## 五、什么时候能停

- **能停**：前沿为空，并且共识小结已经被用户确认。
- **不能停**：台账里还有「待问 / 待答复」；或者用户的回答含糊（「差不多」「先这样」），这类回答要再追问一次具体选哪个。
- **用户答不上来**：不替他编。给他三条路选：去问清楚再继续；按推荐先做并标「按推荐」（记下原话）；移出本轮。
- **问题多到问不完**：这不是少问的理由，是范围太大的信号。回到阶段 0，把纵切再切小。
