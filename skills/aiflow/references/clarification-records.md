# 澄清归档

仅在共识收口后，或用户明确要求中途保存时读取。访谈方法见 `clarification.md`。

## 新建与续写

新项目收口后，由主智能体建立 `.aiflow/artifacts/`，整理 `state.yaml`、`questions.md` 并派对应角色编写当前阶段产物，按需建立断点日志。按实际执行填写 `mode`、工具返回的 `agent_sessions` 及本阶段角色完成后的 `stage_dispatch`；复用会话也要有本阶段的新任务和返回。阶段 0 使用 facts v0；阶段 1 需求收口后才创建 `facts.md` v1。已有项目追加本轮记录，保留历史答复与真实确认，不覆盖成一场新访谈。

问题台账依据对话整理，保留编号、展示过的推荐、实际答复与有意义的依赖；选项与组合限制按需放备注。无法从对话恢复的用户决定仍是未决项，不能补造原话。查证来源及限制归入调研记录，纯事实查证无需伪装成用户问题。

## 状态记录

`state.clarification` 对应当前阶段：

- `pending`：正在访谈或等待共识确认。既有项目进入阶段 0–4，或任何阶段出现新决策时设置；保留先前共识历史，清空本轮的 `summary`、`user_quote`、`confirmed_at`。
- `confirmed`：前沿为空，用户已确认完整共识。填写 `stage`、`summary`、真实 `user_quote` 与含时区的 `confirmed_at`。
- `not_needed`：已有输入完整明确，无需新澄清。`summary` 写明来源与理由，不编造用户原话；本阶段有非作废访谈问题时使用 `confirmed`。

没有状态文件的访谈依据当前对话续问；`状态` 或 `继续` 也不要求先初始化。缺少先前上下文时说明缺口，再恢复访谈。

## 问题台账

沿用 `templates/questions.md` 的列和以下状态，以兼容门禁：

| 状态 | 使用条件 |
|---|---|
| 待问 | 已识别，前提尚未明确 |
| 待答复 | 已提问，尚无明确答复 |
| 已解决 | 用户明确回答，保留原话 |
| 按推荐 | 用户接受已展示的推荐，保留原话 |
| 移出本轮 | 用户同意暂缓，保留原话 |
| 作废 | 前提改变使问题不再成立，备注说明原因 |

通常在收口后落档，届时不应有前两种状态。中途保存或续跑旧记录时可以保留未决项；`pending_decisions` 与**已落档**的「待问 / 待答复」编号一致，不要求为每轮对话同步写文件。多选答复保留全部所选项和补充说明。

共识确认之后，才整理 intake、facts、PRD、原型、设计、架构或选型等当前产物并登记 `artifacts`。需评审的产物按 `review.md` 处理；理解一致的确认不自动认可尚未展示的具体内容。

阶段收尾运行 `check.py`。访谈期间缺少文件是正常状态，检查器应阻止提前推进，而不是要求先补文件。检查通过只能证明记录满足门禁，不能证明问题想全或原话真实。
