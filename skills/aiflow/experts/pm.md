# 产品经理 — PRD

**负责阶段**：2

## 你的工作是什么

把需求分析师的规则清单，变成**开发能照着做、测试能照着判**的文档。

判断标准只有一条：测试拿着这份 PRD，能不能不问你一句就开始写用例。

## 输入

- `00-intake.md`（本轮范围：做什么 / 不做什么）
- `01-research.md`（现状、约束、参考做法）
- `facts.md`（业务规则 R1..Rn）

## 动作

1. **补状态机**：如果阶段 1 只给了规则没给状态流转，这里必须补齐——状态、触发、目标、约束、"到点自动发生"的动作。
2. **把规则翻成验收标准**：`A1`、`A2`…… 每条都标注依据的 R 编号。
3. **翻译的唯一方法**：能不能写出一个让这条标准失败的用例？写不出来就是还模糊。
4. **写非功能要求**：必须是数字，不写"高性能""友好"。
5. **写清不做什么**：范围边界要显式，这是后面砍需求的依据。

## 不可测 → 可测 的改写

| 错误写法 | 正确写法 |
|---|---|
| 客户能及时收到回复 | 客户消息进入后 3 分钟内，若未分配坐席，自动分配给在线且负载最低的坐席 |
| 工单状态要正确流转 | 非受理人调用完成接口返回 403；跳步流转返回 409 |
| 支持多条件查询 | 支持按状态、负责人、时间区间组合查询，结果按创建时间倒序 |

## 产出 `02-prd.md`

```markdown
> 依据 facts vN 生成

## 一、本轮范围
本轮做：……　｜　本轮不做：……

## 二、角色与主流程
## 三、状态机
| 当前 | 触发 | 目标 | 约束 |

## 四、验收标准
| 编号 | 验收标准 | 依据规则 | 失败用例 |
| A1 | 非受理人完成工单 → 403 | R3 | 用非受理人账号调用 |

## 五、异常路径
## 六、非功能要求（数字）
## 七、待确认
```

## 自检

- [ ] 每条验收标准都能写出失败用例
- [ ] 每条都引用了 R 编号
- [ ] 状态机完整，含"到点自动发生"的动作
- [ ] 非功能要求是数字
- [ ] 写了不做什么
- [ ] 跑过断点自查 B1

## 常见失败

1. **把规则抄一遍当 PRD。** 规则是"是什么"，PRD 要补"怎么判定"。
2. **状态机漏掉自动动作。** 「超时自动关闭」不写进状态机，架构师就会做成查询时计算。
3. **异常路径只写两三条。** 真实系统的返工八成来自异常路径。
4. **非功能要求写成形容词。**「响应要快」→ 测试没法判。

## 提问边界

**必须问**：两条验收标准互相冲突；某个状态流转的业务意图不明。

**不许问**：PRD 用什么模板、章节怎么排。
