# 配置模型与项目规范

这份指南面向使用 aiflow 的人：配置放在哪里、每个字段是什么意思、怎样交给 AI 使用，以及怎样确认已经采用。

快速入口：[文件位置](#文件放在哪里) · [模型字段](#每个字段的含义) · [全部角色与身份](#角色与身份完整清单) · [阶段编号](#阶段编号) · [前后端开发规范](#前后端开发规范) · [设计规范](#设计规范) · [技术栈与部署资料](#技术栈与部署资料) · [常见问题](#常见问题)

## 文件放在哪里

以下“项目”都是**你正在交付的业务项目**。把配置放在业务项目中，已安装的 aiflow 技能目录用于提供脚本、模板和示例。

| 你想控制什么 | 项目文件 | 不提供时 | 填好的示例 |
| --- | --- | --- | --- |
| 各阶段、各角色使用的模型 | `.aiflow/models.json` | 沿用宿主默认选模 | [模型示例](examples/models.json) |
| 前端代码组织、请求、类型与检查要求 | `.aiflow/frontend-standards.md` | 查团队默认；仍没有则沿用项目代码和工具配置 | [前端规范示例](examples/frontend-standards.md) |
| 后端接口、数据、JOB 与检查要求 | `.aiflow/backend-standards.md` | 查团队默认；仍没有则沿用项目代码和工具配置 | [后端规范示例](examples/backend-standards.md) |
| 颜色、字体、圆角、布局与状态表达 | `.aiflow/design-system.md` | 需要原型或设计时，由 AI 根据现有界面、你提供的资料和团队规范整理；仍无依据时与你确定 | [设计规范示例](examples/design-system.md) |

最容易的用法是：选择需要的示例，按自己的项目修改，然后把文件位置告诉 AI。已有规范可以保留原位置，具体方式见下文。模型配置和开发规范都可不设置；只有需要原型或设计稿时，才需要形成项目设计规范。

例如，在已加载 aiflow 的会话中发送：

```text
请使用本项目 .aiflow/models.json 配置阶段角色模型。
前端规范在 .aiflow/frontend-standards.md，后端规范在 .aiflow/backend-standards.md。
视觉要求参考 .aiflow/design-system.md。
先读取并告诉我实际采用了哪些文件、有没有冲突，再按当前流程继续。
```

你可以预先准备这些配置；首次需求访谈不要求先创建它们。没有配置文件时，也可以先把要求告诉 AI，由它在共识确定后整理。`state.yaml`、模型执行记录和确认结果由 AI 根据实际过程维护，使用者无需预填“已通过”。

## 模型配置

### 先看一个能理解的例子

创建业务项目的 `.aiflow/models.json`：

```json
{
  "schema_version": 1,
  "default": "inherit",
  "profiles": {
    "coding": {"model": "<开发模型ID>"},
    "deep": {"model": "<分析模型ID>", "reasoning_effort": "high"}
  },
  "roles": {
    "aiflow-frontend": "coding",
    "aiflow-backend": "coding",
    "aiflow-test": "deep"
  },
  "stages": {
    "6": {"roles": {"aiflow-backend": "deep"}},
    "9": {"default": "deep"}
  },
  "on_unavailable": "error"
}
```

先把两个 `<…模型ID>` 替换成**当前宿主实际支持的模型标识**，并确认所选模型支持 `high`；不需要指定推理强度时删掉 `reasoning_effort`。不要把示意值直接用于真实派工。可先让 AI 查看当前工具可用的模型与选模能力，不需要在这个文件里填 API Key。

`coding`、`deep` 是你给模型组合取的名字，可以改名；它们不是模型 ID。这个配置表示：前后端通常使用 `coding`，测试使用 `deep`；阶段 6 的后端单独改用 `deep`；阶段 9 中实际派出的角色默认使用 `deep`；其余没有命中规则的角色继承宿主默认。

[基础模型示例](examples/models.json) 与上面的 JSON 一致，展示常用专业技能的配置。[全量模型示例](examples/models-advanced.json) 列出了全部 11 个可配置目标，每一项的中文含义、使用阶段和兼容键见 [完整清单](#角色与身份完整清单)。[空白模板](templates/models.json) 全部继承宿主设置，适合从零逐项添加。完全沿用宿主时可以不创建模型配置文件。

### 每个字段的含义

下表的点号表示嵌套关系，例如 `profiles.coding.model` 是 `profiles` 对象中 `coding` 的 `model` 字段。

| 字段 | 类型与是否必填 | 默认值 | 含义与填写方式 |
| --- | --- | --- | --- |
| `schema_version` | 整数，必填 | 无 | 配置格式版本，目前填写数字 `1`；不要写字符串 `"1"`。 |
| `default` | 字符串，可省略 | `"inherit"` | 项目默认采用哪个模型组合。填写 `profiles` 中的名称，或 `"inherit"`。 |
| `profiles` | 对象，可省略 | `{}` | 定义可复用的模型组合。一个组合包含一个模型，以及可选推理强度。 |
| `profiles.<名称>.model` | 非空字符串，每个组合必填 | 无 | 宿主提供的真实模型 ID。它不是角色名，也不是 `coding` 这样的组合名。 |
| `profiles.<名称>.reasoning_effort` | 非空字符串，可省略 | 所选模型在宿主中的默认值 | 推理强度，例如宿主确实支持的 `high`。支持范围随宿主与模型而定，aiflow 不硬编码统一名单。 |
| `roles` | 对象，可省略 | `{}` | 派工目标的默认组合，支持八个专业角色和三个运行身份，全部合法键见 [完整清单](#角色与身份完整清单)。值填写组合名或 `"inherit"`。 |
| `stages` | 对象，可省略 | `{}` | 按阶段覆盖规则。键是 `"0"` 至 `"11"` 的字符串，值是该阶段的配置对象。 |
| `stages.<阶段>.default` | 字符串，可省略 | 继续查角色默认、项目默认 | 该阶段所有实际派工身份的默认组合，优先于项目级 `roles`。 |
| `stages.<阶段>.roles` | 对象，可省略 | `{}` | 仅为该阶段中的某个角色选组合，优先于该阶段 `default`。 |
| `on_unavailable` | 字符串，可省略 | `"error"` | `"error"`：显式选模不可用或无法核实时暂停受影响派工；`"inherit"`：允许取消显式模型及推理覆盖，回退宿主默认，并记录原因。 |

组合名以英文字母开头，后面可包含字母、数字、下划线和短横线；`inherit` 是保留字。`roles` 中的值只能是已定义组合名或 `inherit`，不能直接放模型对象。JSON 使用双引号，不支持注释、尾逗号、重复键或未声明字段；字段解释放在本指南中。

### 角色与身份完整清单

当前支持 **11 个独立配置目标：八个专业角色，加三个运行身份**。下面是完整清单；“兼容键”是同一目标的旧写法，不增加角色数量。专业角色推荐用完整技能名，运行身份直接用其固定键。

| 模型配置键 | 兼容键 | 中文名称与含义 | 使用阶段或条件 | 有独立技能 | 全量示例中的值 |
| --- | --- | --- | --- | --- | --- |
| `aiflow-analyst` | `analyst` | 需求分析师：澄清目标与范围、调研、整理业务事实。 | 0、1 | 有，同名技能 | `deep` |
| `aiflow-product` | `pm` | 产品经理：编写 PRD 与验收标准，需要时制作产品原型。 | 2 | 有，同名技能 | `deep` |
| `aiflow-design` | `designer` | 体验设计师：制作设计图片与 HTML，走查实现并复核修复。 | 3、7；9 按需复查 | 有，同名技能 | `deep` |
| `aiflow-architect` | `architect` | 技术架构师：技术选型、架构与契约设计、任务拆分。 | 4、5 | 有，同名技能 | `deep` |
| `aiflow-frontend` | `fe` | 前端开发工程师：页面与交互实现、接口联调、前端及走查问题修复。 | 6；7、9 按任务需要 | 有，同名技能 | `coding` |
| `aiflow-backend` | `be` | 后端开发工程师：接口、数据与 JOB 实现，后端缺陷修复。 | 6、9 | 有，同名技能 | `coding` |
| `aiflow-test` | `tester` | 测试工程师：架构可验收性试读、代码审阅、测试、缺陷复测和回归。 | 4 试读；8、9、10 | 有，同名技能 | `deep` |
| `aiflow-release` | `operator` | 运维工程师：核验部署条件，准备和执行发布、回滚及部署验证。 | 11，仅本轮需要部署时 | 有，同名技能 | `inherit` |
| `coordinator` | 无其他别名 | 阶段执行协调器：安排角色派工、重试与评审，汇总结果；专业产物由专业角色完成。 | 3、4、6、7、9，采用协调器执行时 | 无，运行时会话 | `inherit` |
| `design_reviewer` | 无其他别名 | 独立设计评审者：对照确认图片、HTML、截图和设计依据检查设计稿，与出稿会话分开。 | 3，最终 HTML 交付前 | 无，运行时会话 | `independent` |
| `final_reviewer` | 无其他别名 | 独立终验者：模式 3 下以独立模型完成终验；人工终验沿用人工路径。 | 10，采用模型终验时；11 可沿用仍有效结果 | 无，运行时会话 | `independent` |

每一行都可用于项目 `roles`、阶段内的 `stages.<阶段>.roles`，以及模型解析器的 `--role`、`--override`、`--model`、`--reasoning-effort`。例如，项目级 `"aiflow-product": "deep"` 为产品经理选组合；阶段级 `"4": {"roles": {"aiflow-test": "independent"}}` 只调整阶段 4 的测试试读会话。同一映射里不要同时填写一个目标的完整名与兼容键。

表中的 `coding`、`deep`、`independent` 对应 [全量示例](examples/models-advanced.json) 的三个 `profiles`，只演示组合如何引用，不是固定的模型搭配建议；`inherit` 表示显式继承宿主设置。各角色都可以换用你定义的其他组合，也都可以省略。省略时按阶段默认、项目默认等剩余规则解析；全量示例中的角色默认也会被阶段配置覆盖。

清单覆盖全部可配置派工目标，以下容易混淆的名称有其他用途：

| 名称 | 实际含义 | 应怎样处理 |
| --- | --- | --- |
| `aiflow` / 主会话 | 主控技能和当前与用户对话的会话 | 不属于本 JSON 的选模目标；主会话模型由宿主设置控制。 |
| `FE`、`BE`、`JOB` | 任务类型 | 前端配置 `aiflow-frontend`；BE 和 JOB 都配置 `aiflow-backend`。 |
| `developer` | 旧项目保留的开发身份记录 | 不作为模型配置键，按本次任务分别使用前端、后端角色。 |
| `human:<姓名>` | 模式 3 人工终验的记录标识 | 由流程登记实际人工终验；不放进模型 `roles`。 |

### 阶段编号

`stages` 的键采用下表字符串。配置某个阶段或身份只决定实际派工时如何选模，不会增加流程阶段、启用原本不需要的角色，或代表已经安装相应技能。

| 阶段键 | 工作内容 |
| --- | --- |
| `"0"` | 需求澄清 |
| `"1"` | 需求调研 |
| `"2"` | PRD 与产品原型 |
| `"3"` | 设计稿，需要时执行 |
| `"4"` | 技术架构 |
| `"5"` | 任务拆分 |
| `"6"` | 前后端开发 |
| `"7"` | 设计走查，需要时执行 |
| `"8"` | 代码审阅与测试 |
| `"9"` | 缺陷修复与复测 |
| `"10"` | 全量回归 |
| `"11"` | 上线，本轮需要部署时执行 |

### 额外调度身份（进阶）

完整清单中的三个运行身份由主控按 [调度协议](references/orchestration.md) 安排，不需要另装技能。主会话创建阶段协调器；协调器为专业角色和设计评审者分别派工。宿主不能嵌套派工而采用直接派工时，本阶段由主会话承担协调并直接派角色及评审会话。模式 3 的模型终验由主控安排，终验身份与执行角色和协调器分开。

进阶示例中的 `"coordinator": "inherit"` 表示协调器的**角色默认**沿用实际派工方的宿主设置；更高优先级的阶段配置仍可覆盖它。例如进阶示例阶段 9 的 `default: deep` 也会作用于本阶段协调器。

`"design_reviewer": "independent"` 表示设计评审会话选用 `profiles.independent`。`independent` 只是示例自定义的组合名，可以改名；它不会自动创建评审者，也不证明实际模型不同。独立性由单独的会话和实际执行证据保证，要求不同模型时还要核对实际模型。

这些模型配置均可省略。流程需要协调器或评审者时，主控仍按协议安排，其模型继续按阶段默认、项目默认等规则选择；省略配置不等于关闭评审。[全量模型示例](examples/models-advanced.json) 已把它们与八个专业角色全部列出，其中的模型 ID 仍需替换为宿主实际支持的值。

### 多个规则同时命中时用哪个

从高到低依次是：**本次明确指定 → 阶段内角色 → 阶段默认 → 角色默认 → 项目默认**。

以上面的 JSON 为例：

| 本次派工 | 选中的组合 | 原因 |
| --- | --- | --- |
| 阶段 6，前端 | `coding` | 使用角色默认。 |
| 阶段 6，后端 | `deep` | 阶段内角色覆盖了后端默认。 |
| 阶段 9，前端 | `deep` | 阶段默认高于项目级角色默认。 |
| 阶段 9，明确临时指定后端用 `coding` | `coding` | 本次明确指定优先。 |
| 阶段 4，架构师 | `inherit` | 其余规则未命中，使用项目默认。 |

选中的是整个组合，不把上一个组合的推理强度拼到新模型上。显式 `inherit` 会停止继续查找：它表示沿用实际派工方的宿主默认设置，而不是“退回上一层规则”。因此，想让某角色随项目默认变化时，通常从 `roles` 中省略该角色即可。

### 怎么启用、查看和修改

保存项目配置后，在 aiflow 会话中发送：

```text
请读取 .aiflow/models.json，预览阶段 6 的前端和后端会使用哪个模型，
列出命中的配置、宿主能否应用，以及哪些实际模型值尚未验证。
```

也可使用入口命令 `/aiflow 模型` 查看当前模型状态。运行中的结果以本阶段固定的配置快照为准；未运行的配置只能预览。主控负责保存快照与实际执行记录。

如需自行检查 JSON，先取得实际安装的 aiflow 技能目录，替换下面两个目录占位值后运行：

```bash
python "<aiflow技能目录>/scripts/resolve_models.py" "<业务项目目录>" --stage 6 --role aiflow-frontend --role aiflow-backend
```

这个命令只读取文件。`ok: true` 表示解析及已提供的能力检查未阻塞；`launch` 是准备传给宿主的参数，不代表已经创建了子智能体。`availability: unverified` 表示能力信息不足，实际派工时还要核实。输出里的 `fe`、`be` 是内部键，旁边的 `skill` 会显示对应完整技能名。

外部配置可以保留原位置：告诉 AI“本项目采用 `docs/agent-models.json`，后续阶段继续使用它”；手工预览时在上述命令追加 `--config "<该文件绝对路径>"`。模型配置没有自动读取 `~/.aiflow/models.json` 的团队默认规则；需要共用模型配置时显式指定外部文件。

只改当前一次派工，可以说“本次阶段 6 后端改用已定义的 `coding`，其他角色沿用当前配置”；命令行预览可追加 `--override aiflow-backend=coding`。直接指定模型用 `--model "aiflow-backend=<实际模型ID>"`；要同时指定推理强度，再加 `--reasoning-effort aiflow-backend=high`。后一个参数必须与同一角色的 `--model` 一起使用。

磁盘配置修改默认在下次进入阶段时采用。同阶段立即换模时，明确告诉 AI 它应影响哪些角色；AI 会保存新修订、为请求设置改变的角色新建会话并重新派工。加载一个独立角色技能仍使用当前会话；这份 JSON 主要控制 aiflow 的子智能体派工，不会切换主会话模型。

## 前后端开发规范

### 从示例开始，或直接采用现有文件

[前端完整示例](examples/frontend-standards.md) 已写好目录职责、接口类型、页面状态、请求竞态、提交与权限反馈、视觉依据和检查方式。[后端完整示例](examples/backend-standards.md) 已写好分层、输入校验、事务、接口结构、日志、JOB、测试和交接要求。

它们是可删改的规则示例，不会自动变成团队要求。采用前删除不适用条目，补上项目已有命令和真实约束。已有规范 Markdown 可以原样使用；不要求固定标题、表格或规则编号。空白骨架另见 [前端模板](templates/frontend-standards.md)、[后端模板](templates/backend-standards.md)。

前端规范示例适用于 TypeScript 页面，后端示例适用于 HTTP JSON 接口。其他语言或交付形态按实际项目改写；不会因为复制示例就更换已确认技术栈。

例如，规范文件已经在业务仓库的 `docs/standards/` 中，可以直接说：

```text
前端按 docs/standards/frontend.md 开发和修复，
后端及 JOB 按 docs/standards/backend.md 执行。
请完整读取两份文档，登记采用路径，指出与当前技术栈或设计的冲突。
交付时列出实际检查结果及未满足条目。
```

AI 登记后的状态片段形如下面这样；这是路径说明，无需手工创建整份状态文件：

```yaml
development_standards:
  frontend: "docs/standards/frontend.md"
  backend: "docs/standards/backend.md"
```

这里的 `frontend`、`backend` 是**开发规范路径字段**，与模型配置中的 `aiflow-frontend`、`aiflow-backend` 用途不同。

| 路径规则 | 含义 |
| --- | --- |
| 显式路径 | 优先采用本轮指定或已登记文件；相对路径以业务项目根目录为准，也支持绝对路径和 `~/`。 |
| 项目默认 | 未指定路径时，查 `.aiflow/frontend-standards.md`、`.aiflow/backend-standards.md`。 |
| 团队默认 | 项目也没有时，查用户主目录 `~/.aiflow/` 下同名文件；Windows 的 `~` 是当前用户主目录。 |
| 省略一端或写 `""` | 该端继续自动查找默认文件，不代表禁用默认规范。 |

两端分别选择来源，不会自动合并项目与团队的同类规范。需要组合多份时，告诉 AI 要采用哪些文件以及冲突时以谁为准，再整理项目版本。一份综合规范也可以同时指定给两端。指定路径不存在、文件为空或不可读时，会报告具体问题，不会静默换用另一份。

### 怎样确认开发规范已经采用

架构前让 AI 列出两端实际读取的规范路径；开发或修复后查看实际检查证据。全流程中，阶段 6 的 `06-dev-log.md` 有「开发规范执行」表，FE、BE 分别记录规范文件、自检结论和证据，JOB 使用 BE 行。单角色任务用现有交付记录即可。

例如可以问：“这次采用的是哪一版前端规范？FE-02 类型检查和 FE-03 请求失败状态分别怎么验证？把未满足项列出来。”示例中的编号方便核对，自有规范没有编号也可以按条目名称询问。

门禁检查文件是否存在、记录是否对应以及是否有真实检查依据；它不会自动理解任意 Markdown 并证明全部规则已落实。中途修改规范时，告诉 AI 改了哪些要求，让它重读并检查受影响代码；新旧结果保留在对应记录中。

## 设计规范

### 从填好的设计规范开始

[设计规范示例](examples/design-system.md) 包含蓝色主色、正文与背景色、字号、圆角、导航布局、窄屏处理和状态标签；[空白模板](templates/design-system.md) 保留完整字段供你填写。

希望采用示例时，将其修改为项目实际要求，交给 AI 整理到 `.aiflow/design-system.md`。例如：

```text
请参考我准备的 docs/design-system.md 整理本项目设计规范。
主色用 #2563eb，普通控件圆角 6px，页面标题 20px；
已有页面的组件库继续沿用。先列出从资料提取的规则和仍需决定的差异，
随 PRD 一起确认后，让原型、设计稿和前端实现采用同一份规范。
```

### 设计文件里的字段是什么意思

| 内容 | 怎么填写 | 怎样使用 |
| --- | --- | --- |
| 来源 | 已有主题、团队规范或你选择的示例及版本 | 说明设计依据；需要原型或设计时，门禁检查来源已填写。 |
| 组件库 | 已使用或已确认的组件库及版本；尚未指定可写“无”并说明 | 纳入技术栈讨论；它不是安装依赖的命令。 |
| 样式预设 | `无` 或已提供的 `element-plus` | 原型工具加载对应样式预设；`无` 表示不加载额外预设，保留内置基础样式。 |
| 规范文件、依据 | 原文路径、主题文件位置或用户决定的依据 | 便于核对从哪里提取了规则。 |
| 令牌表的“变量” | 样式包支持的 CSS 变量名，如 `--primary`、`--radius` | 构建时按变量名覆盖；保留“变量”“取值”这两个列名。 |
| 令牌表的“取值” | 颜色如 `#2563eb`，尺寸如 `6px`；写“按默认”则不覆盖 | 使用真实设计值；修改支持的基础色后会派生浅色背景、边框与文字色。 |
| `--check-*` 行 | 允许值列表，如 `12 14 16 20`，以空格分隔，单位按说明为 px | 定义检查允许的范围；不会把页面控件尺寸自动改成这些值。 |
| 布局 | 导航、内容宽度、间距、不同设备下的行为 | 由设计和开发落实，不能只靠令牌表完成。 |
| 状态与标签类型 | 实际状态对应 `primary / success / warning / danger / info` | 统一状态语义；文字与颜色共同表达。错误色变量是 `--error`，标签类名是 `danger`。 |
| 规范没覆盖的 | 本次需要补充或沿用组件库默认的部分 | 显示仍需作决定的边界。 |

查找顺序是：已有项目设计规范 → 已有前端主题 → 你提供的资料 → 团队默认 → 与你澄清。你明确要求替换已有设计时会按该要求处理冲突；来源排序不用于覆盖本轮决定。团队默认放 `~/.aiflow/design-system.md`，AI 在项目采用时复制整理为项目版本。

已有品牌文档、主题令牌、截图都可提供给 AI；无法直接读取的设计平台内容可导出到 `docs/design/`。不必亲自把全部资料转成令牌表，AI 会提取并列出缺口。

### 怎样确认设计规范生效

先核对 `.aiflow/design-system.md` 中的来源、实际取值及 PRD 中的采用说明，再看原型、设计图和实现。模型配置只负责选模，开发规范主要约束代码；视觉规则由这份设计规范承担。

使用内置 HTML 工具时，产物目录形如：

```text
.aiflow/
  design-system.md
  prototype/
    build.py
    _src/
      kit.css
      index.html
```

AI 在业务项目里复制并使用工具。`build.py` 会读取旁边上一级的 `design-system.md`；运行日志会列出实际覆盖的令牌，并生成 `_built.css`。只在采用这个工具时执行 `python "<业务项目目录>/.aiflow/prototype/build.py"`。

这只证明令牌被构建器读取；自然语言布局、交互以及真实应用的主题接入仍需逐项实现，并通过浏览器和设计走查核对。设计确认后改规范时，告诉 AI 改动范围，复核受影响的设计和实现，不能用改规范来掩盖现有偏差。

## 技术栈与部署资料

它们也可以先用自然语言或现有文档提供，不放进 `models.json`：

| 想提供的要求 | 可以直接发给 AI 的例子 | 后续怎样处理 |
| --- | --- | --- |
| 沿用已有技术栈 | “前后端沿用当前依赖和锁文件，不主动换框架；数据库要求见 docs/architecture.md。列出还需选择的部分。” | AI 核对现状，在阶段 4 整理实际选型、版本及取舍，确认后锁定。 |
| 指定与偏好区分 | “后端语言必须沿用现有项目；缓存不是必须，请按实际需求提出方案。” | 必须项、偏好和项目现状分别记录，不把偏好当强制选型。 |
| 不包含本轮部署 | “本轮交付代码、运行说明和测试结果，不发布到服务器。” | 随 PRD 确认交付范围；回归通过后交付，跳过上线阶段。 |
| 提供已有部署资料 | “本轮需要部署到测试环境，参考 docs/deployment.md；先核对项目依赖和文档，列出缺失条件。” | 运维沿实际构建、运行和外部依赖核验条件，资料不全的部分再澄清。 |

技术栈细则见 [选型协议](references/tech-stack.md)，记录格式见 [技术栈模板](templates/tech-stack.md)；部署记录格式见 [发布模板](templates/release.md)。这些确认、版本和检查证据应来自实际项目，模板中的“已确认”“通过”不作为默认结果。

## 常见问题

**改了模型 JSON，为什么运行中的角色没变？** 本阶段使用固定快照，保存文件默认只影响下一次进入阶段。需要立即换模时明确告知 AI；既有会话不会因为文件变化自动切换模型。

**主控或单独调用的前端技能为什么仍使用原模型？** 加载技能本身不选模。这份配置用于子智能体派工；主会话模型由宿主控制。

**`fe` 和 `aiflow-frontend` 能同时写吗？** 同一个 `roles` 对象里不可以；它们指向同一角色，会报重复角色。不同层级可采用不同写法，优先级不变。

**把 `default` 改成 `deep`，某个角色为什么还是继承？** 检查该角色或阶段是否显式写了 `inherit`。显式继承也是一条已命中的规则；删除该覆盖，才能继续采用项目默认。

**为什么配置解析成功还显示“未验证”？** 配置解析、宿主是否接受参数和实际运行模型是三件事。主控要根据真实调用和宿主元数据核实，不能仅把请求模型抄成实际模型。

**已有项目或团队规范为什么没有叠加？** 同一端默认选择优先级最高的一份。需要合并时说明采用范围与冲突规则，由 AI 整理项目版本。

**设计令牌明明写了却没变化？** 核对文件是否在构建器上一级、表头是否包含“变量”“取值”、变量是否受支持，以及 `_src/theme.css` 是否在后面覆盖。实际应用还需由前端接入相同视觉规则，原型构建不会直接修改应用代码。

**文档有新字段，但我的脚本仍不支持？** 核对当前会话加载的技能目录。仓库中的修改不会自动同步到已经安装的副本；先更新实际使用的技能，再按这里的例子检查。
