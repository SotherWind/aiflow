# 代码审阅

本文件由 `scripts/bundle_skills.py` 从 `shared/code-review.md` 分发。用于独立代码审阅、开发自检和修复复查；审阅者使用宿主已有的代码读取、搜索、Git 与项目检查工具。

## 1. 确定范围与版本

以用户或派工方指定的范围为准。记录范围来源、基线、目标版本和实际文件清单，再读差异；业务依据来自需求、契约和适用规范，开发者的实现解释不作为正确性证据。

| 输入 | 取范围的方法 |
|---|---|
| 未提交改动 | 同时检查暂存、未暂存和未跟踪文件；已跟踪文件与 HEAD 比较，新增文件读全文 |
| 分支或两个版本 | 先解析真实提交，记录共同祖先与目标提交，再读取两者间差异 |
| 单个提交 | 与其父提交比较；合并提交说明采用哪个父提交，首次提交按新增文件处理 |
| 明确文件、非 Git 项目或缺少开发前基线 | 按授权范围读取完整文件及相关上下文，记录范围依据和限制 |

aiflow 阶段 8 审的是本轮交付代码，包括已提交的开发和走查修复。优先使用派工提供的开发前基线；基线缺失时，由任务与实际实现推导文件范围并审全文。工作区干净只说明没有未提交改动，不能据此跳过本轮审阅。

Git 读取使用 `--no-pager`；diff/show 使用 `--no-ext-diff --no-textconv --no-color`，路径放在 `--` 后并按当前 shell 正确转义。获取失败、输出被截断或基线不存在时，补取证据或明确未完成；大差异分块读完，不以输出前几行代替全量。

文件清单以“路径 + 变更状态”识别；重命名保留旧、新路径，删除后同名重建分别核对。测试、配置、依赖与锁文件、删除文件均纳入判断。删除文件查看旧内容及剩余引用；依赖变化核对实际版本与调用兼容性。生成物、第三方副本或二进制可按相关性排除，但记录原因及采用的替代检查。

每个范围项最终为“已审”“排除”或“未审”。未审写明缺少什么证据；所有应审文件完成后才能报告完整审阅。分别报告总数、已审、排除、未审；如给覆盖率，分母为总数减去有理由的排除项，分母为零写“不适用”。文件审阅覆盖与测试覆盖分别报告。

## 2. 沿实际关系审阅

按共同功能、调用关系与差异大小分批，每批仍逐文件核对。检查修改行所在的完整逻辑，以及会改变结论的调用方、被调用方、类型、配置和测试。发现严重问题后继续完成其余范围。

先检查行为错误与适用约束，再考虑改进建议。优先读取用户和项目规范；格式化、lint 或类型检查已准确覆盖的事项引用工具结果，不重复生成逐行建议。按实际风险选择检查点：

- 输入校验、权限与租户边界、异常和失败分支。
- 资源释放、事务边界、状态迁移、幂等和实际并发访问。
- 接口与配置兼容、依赖 API 是否存在于当前版本。
- 测试是否验证需求，断言是否被删弱，替身是否掩盖真实集成缺口。

这些是查证方向，不是要求每个项目引入相同架构、风格或安全机制。

## 3. 核实发现

每个候选问题都回到具体代码和生效前提，检查可能推翻它的证据：上游是否已校验、类型或契约是否排除该输入、调用路径是否可达、资源是否由外层管理。并发问题核实共享状态与实际并行路径；性能问题说明规模或热点依据；注入类问题追踪输入来源与已有处理。

确认的问题给出真实文件位置（删除处注明旧版本）、触发条件、实际影响、依据和修复方向。证据可为代码路径推导、项目工具输出或最小复现；如实区分静态判断与实际执行。位置暂时无法确认就继续定位，不生成猜测行号。

| 判定 | 如何处理 |
|---|---|
| 已证实缺陷 | 说明破坏的需求、契约或技术约束，按影响标 critical / high / medium / low，交对应开发修复 |
| 待核实 | 写明缺少的前提和下一步验证；对完成审阅必需的验证仍待完成时，报告审阅未完成 |
| 改进建议 | 说明收益和适用条件，和缺陷分别呈现；不因个人风格偏好阻塞交付 |

严重性表示影响，不表示可信程度。证据推翻的候选不作为发现报告；未核实的严重疑点保留限制，不能伪装成已证实缺陷或无问题。报告前合并同一根因的重复发现，并复核位置、前提和修复方向。

## 4. 交付与修复衔接

独立审阅直接交付范围、覆盖情况、发现与限制；仅请求审阅时以只读方式完成。用户同时要求修复时，按已有授权修复并验证；角色协作中的代码修改仍交对应开发，独立审阅和复测由测试角色负责。

aiflow 阶段 8 将记录放入 `08-test-report.md` 的“代码审阅”，与按任务测试结论分别保留。每条 BUG 必须明确填写“验证类型：验收”或“验证类型：技术”。可复现的验收缺陷使用既有 T/A/E 关系；已证实但只违反技术约束的缺陷仍使用 BUG 编号和任务归属，以“技术依据 + 技术检查 + 复测证据”闭环，详情格式见主控的 `templates/technical-bug.md`。纯建议不建阻塞缺陷，现有验收失败也不能通过改成技术缺陷免除复测。

阶段 9 修复后重新查看补丁及受影响调用路径，把本次目标版本、范围和复查证据记入缺陷单；阶段 10 重跑技术缺陷的检查项，和业务全量回归分别留证。初测审阅记录保持历史，后续结果追加在修复和回归产物中。审阅期间或之后代码又变更时，重新核对清单并复查受影响部分；旧结果仅对已审版本成立。
