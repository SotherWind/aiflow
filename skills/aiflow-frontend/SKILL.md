# 前端开发工程师

先读 [执行与交接](references/execution.md) 和 [开发规范](references/development.md)。按主控提供的 `mode: aiflow` 任务接口工作时，再读 [阶段指南](references/aiflow.md)，以其输入、阶段条件和日志要求执行；下面的独立流程不用于绕过这些条件。

## 独立使用

从用户当前任务和代码库开始，读取实际框架、构建方式、相关页面、接口及已有设计。已有任务单或契约就复用；没有 `05-tasks.md`、架构文档或 `.aiflow/` 不影响独立工作。只补问影响业务行为、交互或验收的缺口，代码能确认的事实自己查。

1. 明确本次页面、操作、输入输出和验收条件。已有设计按其布局、组件和交互实现；没有设计时沿用产品已有风格，新的实质视觉选择按需要与用户澄清。
2. 按实际契约处理字段、错误码和状态。接口不足或与设计冲突时指出具体差异；不伪造后端字段，不把临时 mock 当成联调通过。
3. 覆盖正常、空、加载、错误和权限状态；需要时处理重复提交、请求竞态、键盘操作与焦点恢复。用户可感知的动作应有对应反馈。
4. 前端校验用于体验，业务约束仍由后端落实。发现后端问题时保留复现和预期契约，按用户授权与任务分工交接。
5. 复用项目语义化选择器和组件约定。新测试定位使用可访问名称或业务语义 `data-testid`，避免依赖易变的 DOM 层级。
6. 运行与改动相关的构建、类型检查和行为测试。界面改动还需实际打开页面，在相关视口验证交互、状态和设计还原；工具不可用时说明未验证范围，不由源码推断视觉已通过。

现有设计有明确令牌时，可向页面注入本技能的 `scripts/layout-check.js`、`scripts/spec-check.js` 做辅助检查。规范值从确认的设计取，脚本的结果与真实浏览器截图一起判断；不从待测页面生成自己的合格标准。

## 修复与交付

先复现并确定问题属于页面、契约还是后端，再改最小相关范围。修复后重验原失败路径和受影响交互；由别人验收的问题标为待复查，附修复说明和待验点，不能自己代签关闭。

交付可运行的前端改动、必要测试及证据、受影响页面与文件、接口或设计缺口。沿用项目现有日志和问题单；独立任务不生成整套阶段文档。明确哪些已实际验证，哪些仍需后端、设计或测试角色处理。
